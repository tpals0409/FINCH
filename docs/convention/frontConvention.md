# 프론트엔드 크로스파트 계약

이 문서는 **프론트엔드가 다른 파트(백엔드·AI·인프라)와 공유하는 계약만** 담는다.
데이터 표기, API 응답·에러 형태 전제, 브라우저 제약이 여기 들어간다.

> **프론트 내부 규약은 [`frontend/docs/frontConvention.md`](../../frontend/docs/frontConvention.md)에 있다.**
> 폴더 구조·네이밍·상태 경계·컴포넌트 규약·반응형 기준은 프론트 안에서만 쓰는 것이므로
> 이 문서에 두지 않는다. 확정·미확정 계약의 현재 상태는
> [`frontend/docs/contracts.md`](../../frontend/docs/contracts.md)에 모아 두었다.

- 작성일: 2026-08-19 / 최종 개정: 2026-08-20 (공통 API 규격 v0.3, AI 파트 회신 반영)
- 브랜치·커밋·MR 절차는 [`gitConvention.md`](./gitConvention.md)를 따르고 여기서 다시 설명하지 않는다

**여기서 정한 것을 프론트가 화면에서 임의로 바꾸지 않는다.
반대로 서버 쪽에서 바꿔야 할 이유가 생기면 코드보다 이 문서를 먼저 고친다.**

## 1. 데이터 표기 규약

| 항목 | 규약 |
|---|---|
| 비율 | **0~1 사이 소수**로 주고받는다. 화면에 그릴 때만 100을 곱해 `%`로 표시한다 |
| 금액 | **원 단위 정수**. 소수점·문자열·콤마 금지 |
| 수량 | 정수 |
| 종목코드 | **6자리 문자열**. 숫자로 다루지 않는다. `005930`의 앞 `0`이 사라진다 |
| 시각 | ISO 8601, KST 오프셋 명시(`2026-08-20T14:32:09+09:00`). 화면 표시는 KST 기준 |
| 등락 색 | 국내 관례를 따른다. **상승 적색, 하락 청색.** 미국식 반대로 쓰지 않는다 |
| 보합 | 상승·하락 어느 쪽 색도 쓰지 않는 중립 색 |
| 등락률 표기 | 부호를 항상 붙인다. `+1.23%` / `-1.23%` |
| 큰 금액 | 한국식 단위로 축약한다. `1.2조`, `3,456억` |

`등락률(changeRate)`의 단위는 문서 간 서술이 엇갈려 있다.
[`frontend/docs/contracts.md`](../../frontend/docs/contracts.md) §3을 보고, 백엔드 회신 전까지는
공통 API 규격 v0.3 §1의 "비율은 0~1 소수"를 따른다.

### 단위 변환 위치

**서버마다 표기가 다르다는 것을 전제한다.** 백엔드는 `camelCase`에 봉투 없이 리소스를 주고,
AI 서비스는 `snake_case`에 공통 봉투를 준다.

**변환과 정규화는 프론트 API 레이어에서 한 번만 한다.**
화면 컴포넌트는 값이 어느 서버에서 왔는지 몰라야 한다.
컴포넌트마다 변환하면 같은 숫자가 화면마다 다르게 보이는 사고가 난다.

## 2. 프론트가 전제하는 API 계약

이 절은 공통 API 규격 v0.3과 AI 파트 명세 §2를 프론트 관점에서 옮긴 것이다.
**원본이 바뀌면 이 문서가 아니라 원본이 진실이다.**

### 2.1 Base URL과 응답 형태

| 항목 | 백엔드(Spring) | AI 서비스(FastAPI) |
|---|---|---|
| Base URL | `/api/v1` | `/api/ai/v1` |
| 필드 네이밍 | `camelCase` | `snake_case` |
| 성공 응답 | 봉투 없이 리소스 본문 | 공통 봉투 |
| 에러 형식 | `{isSuccess, code, message, result}` | `{error:{code,message,detail}, request_id}` |
| 요청 추적 | 응답 헤더 `X-Request-Id` | 본문 `request_id` |

**프론트가 호출하는 Base URL은 `/api/v1` 하나다.** AI 기능도 백엔드를 경유하므로 프론트는 `/api/ai/v1`을 직접 부르지 않는다(§4).
오른쪽 열은 백엔드가 AI를 중계할 때 마주치는 형태이고, 프론트에는 백엔드가 재포장한 결과가 온다.

**중계된 AI 응답이 어느 계열의 형태로 오는지는 아직 확인되지 않았다.** 프론트는 백엔드 형식으로 온다고 가정하고,
AI 봉투가 그대로 실려 오는 경우에 대비해 어댑터를 API 레이어 한 곳에 둔다. 내부적으로는 `{code, message}` 공통 모델로 정규화한다.
정규화 어댑터는 프론트 API 레이어에 두므로, 서버 쪽에서 형태를 맞춰 줄 필요는 없다.

### 2.2 에러 처리

- 에러 판별: `isSuccess === false` 또는 HTTP 4xx/5xx
- **분기는 `code` 문자열로만 한다.** `message` 문장이나 HTTP 상태 코드로 분기하지 않는다
- 따라서 **한 번 배포된 `code` 문자열은 바꾸지 않는다.** 바꾸면 프론트 분기가 조용히 깨진다
- `message`는 사용자에게 그대로 노출한다. 프론트가 문구를 다시 만들지 않으므로 서버가 완성된 한국어 문장으로 준다
- 오류 리포트에는 `X-Request-Id`(AI는 `request_id`)를 담는다. 서버 로그와 잇는 유일한 키다

### 2.3 인증

| 항목 | 계약 |
|---|---|
| 로그인 수단 | **카카오 OAuth 2.0 단일.** 자체 회원가입 폼은 없다 |
| 서비스 인증 | JWT. `Authorization: Bearer <access token>` |
| Access Token | 유효 30분. 응답 본문으로 전달받아 **프론트 메모리에만 보관**(`localStorage` 금지) |
| Refresh Token | 유효 14일. `HttpOnly + Secure + SameSite=Lax` 쿠키로만 전달. JS 접근 불가 |
| 재발급 | `POST /api/v1/auth/refresh` — 본문 없이 쿠키의 Refresh로 새 Access 발급 |
| 401 처리 | `AUTH_TOKEN_EXPIRED` 수신 → refresh 호출 → 성공 시 원요청 재시도, 실패 시 로그인 화면 |
| 사용자 식별 | 토큰에서만 추출한다. 경로·본문·쿼리로 `userId`를 받지 않는다 |

**로컬 개발**: 프론트와 백엔드의 포트 차이로 인한 쿠키·CORS 설정을 각자 맞추지 않는다.
프론트가 **Vite dev proxy로 `/api` 요청을 백엔드에 넘겨 같은 오리진으로 만든다.**
서버 쪽에 로컬 전용 CORS·쿠키 도메인 설정을 요청하지 않는다.

### 2.4 429 `Retry-After`

429 응답에는 `Retry-After` 헤더를 동봉한다.
**프론트는 이 값을 파싱해 그 시간만큼 기다린 뒤 재시도한다.** 헤더가 없으면 지수 백오프로 대체한다.

4xx(429 제외)는 재시도하지 않고, 5xx·네트워크 오류는 지수 백오프로 최대 2회까지만 재시도한다.

### 2.5 멱등성 키

`POST /api/v1/charges`와 `POST /api/v1/orders`는 `Idempotency-Key` 헤더가 필수다.

- **클라이언트가 요청마다 UUID v4를 생성한다**
- 키의 수명은 사용자의 한 번의 클릭이다. **같은 클릭에서 파생된 재시도는 같은 키, 새 클릭은 새 키**
- `409 IDEMPOTENCY_IN_PROGRESS` → 짧게 기다린 뒤 **같은 키로** 재시도한다
- `409 IDEMPOTENCY_CONFLICT`(같은 키 + 다른 본문) → 프론트 버그 신호로 보고 재시도하지 않는다
- **주문 뮤테이션은 자동 재시도하지 않는다.** 멱등 키가 있어도 프론트에서 무한 재시도하지 않는다

### 2.6 커서 페이징

목록 API는 커서 기반이다. offset 페이징은 쓰지 않는다.

```
GET /api/v1/trades?size=30&cursor=trd_01JQZ7X4M9
```

- `size` 기본 30, 최대 100
- 응답은 `{items, nextCursor, hasNext}`
- **커서는 불투명 문자열이다.** 프론트는 파싱·조작·해석하지 않고 `nextCursor`를 그대로 되돌려 보낸다.
  따라서 서버는 커서의 내부 구현(마지막 행 ID, Base64 복합키 등)을 계약으로 노출하지 않아도 되고
  언제든 바꿀 수 있다
- 종료 판정은 `hasNext`로 한다

### 2.7 실시간 시세와 KIS 제약

시세는 **웹소켓 슬롯 + REST 폴링 폴백**의 3층 구조다.
**서버는 어느 경로든 같은 메시지 스키마로 내려보낸다.** 이 전제가 깨지면 프론트가 경로를 인지해야 한다.

- 프론트는 폴링 전제로 먼저 구현하되, `subscribe(ticker, cb)` / `unsubscribe(ticker)` 추상화 계층 뒤에 숨긴다
- 프론트는 **화면에 보이는 종목만 구독한다.** 관심 종목 전체 상시 구독은 하지 않는다
- **슬롯 배분·회수는 서버 책임이다**(참조 카운팅 + LRU). 프론트가 우선순위를 올려보내지 않는다
- 프론트의 책임은 화면 진입 시 구독 신호, 이탈 시 해제 신호를 정확히 보내는 것뿐이다.
  컴포넌트 unmount와 페이지 이탈(`beforeunload`·`visibilitychange`)에서 해제를 보장한다
- 다건 조회 `GET /api/v1/stocks/prices`는 **최대 50건**. 캐시 미스 항목은 `price: null, stale: true`로
  내려오고 프론트는 그 항목만 "시세 지연"으로 표시한다

KIS 실시간 등록 한도는 **서버 전체 합산** 성격으로 전제한다(사용자당 한도가 아니다).
**수치는 미확정이다 — 기능명세 S0-1 실측 대기.** 프론트는 한도 수치를 코드에 상수로 박지 않는다.

### 2.8 주문과 거래 시간

| 항목 | 계약 |
|---|---|
| 주문 유형 | **시장가만.** 지정가·미체결 관리는 확장 범위 |
| 호가창 | 없음 |
| 거래 시간 | **정규장 09:00~15:30 KST 외에는 주문 불가.** 프론트는 주문 버튼을 비활성화하고 이유를 문구로 보여준다 |
| 시세 실패 시 | 마지막 수신 가격 사용 여부와 허용 시간은 미확정(기능명세 S0-3). 허용 범위를 벗어나면 주문 버튼 비활성화 |

## 3. AI 응답 전송 방식 — 일반 요청/응답

**AI 6종은 전부 일반 요청/응답이다. 스트리밍이 아니다.**
`ai/docs/openapi.json`의 6개 엔드포인트가 모두 단일 JSON 봉투(`Envelope`)를 반환한다.

> **SSE는 폐기됐다 (커밋 `34ed34a`, 2026-08-20).**
> 이전 판의 이 절은 "`POST` + SSE라 `EventSource`를 쓸 수 없으니
> `fetch` + `ReadableStream` + `TextDecoder`로 직접 파싱한다"는 요구를 서버 쪽에 남기고 있었다.
> 설계에서 스트리밍이 빠졌으므로 그 요구도 함께 사라졌다.
> **다시 넣기 전에 AI 파트의 구현부터 확인한다.** 문서만 되돌리면 있지도 않은 스트림을 파싱하게 된다.

프론트는 AI 응답도 일반 JSON 요청과 똑같이 다룬다. `shared/api`에 스트림 파서를 만들지 않는다.

## 4. AI 기능 범위

AI 기능은 **6종 전부 MVP 범위**다(AI 파트 회신 ②).
기능 명세서 v2.1의 10.2가 3종으로 적었으나 AI 명세 §1.1의 6종으로 간다.

| 기능 | 화면 | AI 서버 원본 경로 | 프론트가 호출하는 경로 | 전송 |
|---|---|---|---|---|
| AI 종목 분석 | 종목 상세 | `POST /api/ai/v1/stocks/{ticker}/analysis` | `POST /api/v1/ai/stocks/{stockCode}/analysis` (잠정) | 일반 |
| Ask My Portfolio | 채팅 | `POST /api/ai/v1/chat` | `POST /api/v1/ai/chat` (잠정) | 일반 |
| 포트폴리오 진단 | 포트폴리오 | `POST /api/ai/v1/portfolio/diagnosis` | `POST /api/v1/ai/portfolio/diagnosis` (잠정) | 일반 |
| 수익률 원인 분석 | 홈·포트폴리오 | `POST /api/ai/v1/portfolio/attribution` | `POST /api/v1/ai/portfolio/attribution` (잠정) | 일반 |
| 주문 전 점검 | 주문 | `POST /api/ai/v1/orders/preview` | `POST /api/v1/ai/orders/preview` (잠정) | 일반 |
| 데일리 브리핑 | 홈 | `GET /api/ai/v1/briefing` | `GET /api/v1/ai/briefing` (잠정) | 일반 |

**호출 경로는 프런트 → 백엔드 → AI로 확정됐다** (커밋 `34ed34a`, `aa613d7`).
프론트가 쓰는 Base URL은 `/api/v1` 하나이고 AI 서버를 직접 호출하지 않는다.
AI 서버는 사용자 식별을 백엔드의 신뢰 헤더로 받으므로 프론트의 JWT를 직접 검증하지 않는다.

**아직 확정되지 않은 것은 백엔드가 AI를 중계할 때 붙일 경로 문자열이다.** 위 표의 오른쪽 열은 가정값이다.
프론트는 그 경로를 `shared/config` 상수 한 곳에 모아 두고, 회신이 오면 그 파일만 고친다.

**종목코드 파라미터는 `stockCode`로 통일한다.** AI 명세만 `ticker`를 쓰는데 프론트는 백엔드만 호출하므로 백엔드 이름을 따른다.
