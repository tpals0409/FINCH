# S0 결정 — ver2 잠정 기본값 (제안, 미확정)

> **이 문서는 제안이지 확정이 아니다.** 세민의 승인이 있어야 "확정"으로 바뀐다. 아래 값 중 근거가
> "추측"이라고 명시된 것은 실측 전까지 언제든 뒤집힐 수 있다.

## 왜 이 문서가 있나 — "Sprint 0"은 두 가지를 가리킨다

| | SSAFY 원본 | ver2 |
|---|---|---|
| "Sprint 0" | 2026-08-26 **결정 회의**. `S0-1`~`S0-7`은 이 회의에서 팀이 확정하기로 했던 항목 | 기반 구축 스프린트. **2026-09-03 완료** |
| 지금 | — (그 팀은 더 이상 회신하지 않는다) | **Sprint 3** 진행 중 |

`docs/spec/featureSpec.md`·`docs/api/apiSpec.md`·`docs/convention/backConvention.md`의 "Sprint 0"·`S0-N`
표기는 전부 **SSAFY 원본 결정 회의**를 가리킨다. 그 회의는 다시 열리지 않는다 — `featureSpec.md:60`이
"S0-1~S0-4 확정 전에는 차트·체결 가격 소스 구현을 시작하지 않는다"고 못 박아 뒀지만, 확정할 회의 자체가
없다. 이 문서가 그 자리를 대신한다 — **팀 결정 대신 세민의 승인**으로 항목을 닫는다.

## 분류 — 일곱 중 실제로 "정할" 것은 몇 개인가

| # | 주제 | 분류 |
|---|---|---|

| [S0-2](#s0-2--시세-갱신-주기) | 시세 갱신 주기 | **이미 확정** (`apiSpec §5.6` "확정 — STOMP"). 수치 미세조정만 실측 대기 |

실측 없이는 답할 수 없거나(S0-1), 애초에 지금 필요 없다(S0-4).

## S0-1 — 시세 원천 실측

- **원문**: [`featureSpec.md` §1.2 S0-1](./featureSpec.md) · [`apiSpec §5.6`](../api/apiSpec.md) "`[S0-1]` 실측(KIS 실시간 등록 한도·초당 호출 한도·다건 조회 엔드포인트 유무)"
- **분류**: 실측 필요. KIS 앱키 없이는 원천적으로 알 수 없는 외부 플랫폼 제약이라 추측 자체가 무의미하다
- **제안 기본값**: 없음 — 낼 필요가 없다. `apiSpec §5.6`이 이미 **수치와 무관하게 동작하는 구조**를 확정해
  뒀다: 관심도 상위 종목만 KIS 실시간에 등록하고 나머지는 REST 순회로 채워 동일 스키마 캐시에 적재한다.
  "슬롯 한도 수치가 바뀌어도 프론트 계약은 변하지 않는다"(§5.6)
- **누가 막혀 있나**: 아무도. 구조가 이미 수치 무관하게 설계됐다
- **나중에 바꿀 위치**: 백엔드 KIS 수집 워커의 슬롯/순회 설정값(구현 시 백엔드가 정하는 상수)
- **실측 조건**: KIS 앱키 발급 후 (a) 실시간 동시 등록 가능 건수 (b) REST 초당 호출 한도 (c) 다건 조회
  엔드포인트 유무를 측정. 결과로 `apiSpec §5.6` "수치 기본값과 관계식" 표를 **관계식 1~4를 유지한 채**
  조정한다

## S0-2 — 시세 갱신 주기

- **원문**: [`featureSpec.md` S0-2](./featureSpec.md) · [`apiSpec §5.6`](../api/apiSpec.md) (제목 자체가 "확정 — STOMP") · [`apiSpec §13-1·§13-5`](../api/apiSpec.md) · [`contracts.md` P9](../../frontend/docs/contracts.md)
- **분류**: 이미 확정. STOMP 웹소켓 + REST 폴링 폴백, 하트비트 10초(양방향)·3회 미수신(30초)에 슬롯 회수,
  폴링 티어 TTL 30초, 권장 폴링 주기 목록 5초·주문 화면 3초. 프론트는 이미 "폴링 선행 구현으로 진행"을
  결정해 착수했다(`contracts.md` C34)
- **제안**: 추가 제안 불필요. 확정값을 그대로 채택
- **남은 것**: `apiSpec §13-5`가 명시한 대로 수치 자체(하트비트 간격·TTL·폴링 주기·순회 주기)는 **S0-1
  실측 결과에 따라 조정 가능하되 관계식은 유지**해야 한다 — 이건 S0-2가 미정이라서가 아니라 S0-1에 매인
  파생 조정이다
- **누가 막혀 있나**: 아무도
- **나중에 바꿀 위치**: [`apiSpec §5.6` "수치 기본값과 관계식"](../api/apiSpec.md) 표
- **실측으로 갱신할 조건**: S0-1과 동일 (KIS 앱키 실측 후 관계식 유지 하에 조정)

## S0-3 — `stale` 허용 시간

- **원문**: [`featureSpec.md` S0-3](./featureSpec.md) (예시 "60초") · [`apiSpec §5.4`](../api/apiSpec.md)
  `stale` 필드 정의 · [`apiSpec §5.6` 관계식 3](../api/apiSpec.md) "순회 3초 기준 최소 10초 이상 권장" ·
  [`apiSpec §13-2`](../api/apiSpec.md) · [`contracts.md` P10](../../frontend/docs/contracts.md)
- **분류**: 지금 정할 수 있음 — 관계식은 이미 확정돼 있고 구체 숫자만 비어 있다
- **제안 기본값: 15초**
  - **근거**: `apiSpec §5.6` 관계식 3이 "`stale` 허용 시간 > KIS 순회 주기(3초 목표)"이고 "순회 3초 기준
    최소 10초 이상을 권장"한다고 이미 적어 뒀다. 10초는 하한이라 순회 지연이 목표(3초)보다 늘어나는
    상황(네트워크 지연, 일시적 부하)에 여유가 거의 없다. 하한의 1.5배인 **15초**를 여유 마진으로 제안한다
  - `featureSpec`의 "예: 60초"는 이 관계식이 세워지기 전의 막연한 예시다. `apiSpec §5.6`이 순회 주기
    기반으로 훨씬 정교한 하한을 유도했으므로 이쪽을 따른다 — **15초 자체는 추측이다**, 근거가 있는 것은
    "10초 초과"라는 하한뿐이다
- **누가 막혀 있나**: 프론트(주문 화면 "시세 지연" 표시, §7.2 3단계 주문 버튼 비활성화 조건), 백엔드
  (`stale` 판정 로직의 임계 상수)
- **나중에 바꿀 위치**: 백엔드 `stale` 판정 상수(단일 위치, 구현 시 백엔드가 정함). 관계식(> KIS 순회
  주기, 순회 3초 기준 최소 10초 이상)은 반드시 유지
- **실측으로 갱신할 조건**: S0-1 실측으로 KIS 순회 주기가 3초에서 달라지면, 새 순회 주기를 하한으로 놓고
  제안값(하한 × 1.5)을 다시 계산한다

## S0-4 — 분봉 데이터 제공 여부

- **원문**: [`featureSpec.md` S0-4](./featureSpec.md) (7.2·12장에서 "확장 범위") · [`apiSpec §5.3`](../api/apiSpec.md)
  ("`period`: 1M\|3M\|1Y, 모두 일봉 기준. 분봉은 확장 범위") · [`apiSpec §13-3`](../api/apiSpec.md) ·
  [`contracts.md` P11](../../frontend/docs/contracts.md)
- **분류**: 정할 필요 없음. `featureSpec`과 `apiSpec`이 이미 분봉을 MVP 밖(확장 범위)으로 뺐다 — S0-4가
  막는 것은 확장 기능 착수 시점이지 MVP 구현이 아니다
- **제안**: MVP는 일봉(`1M`·`3M`·`1Y`)만 구현한다. 분봉 여부 결정은 확장 단계로 이연
- **누가 막혀 있나**: 아무도 (MVP 범위 안에서는)
- **나중에 바꿀 위치**: `apiSpec §5.3`의 `period`/`interval` 확장 시
- **실측으로 갱신할 조건**: KIS 앱키로 분봉 API 제공 여부·과거 조회 가능 기간을 확인하고, **확장 스코프
  착수 시점에** 재검토한다. 지금은 필요 없다

## S0-5 — AI 읽기 전용 데이터 계약

- **원문**: [`featureSpec.md` S0-5, §10.3](./featureSpec.md) · [`apiSpec §13-4`](../api/apiSpec.md) ·
  [`aiApiSpec.md §4.1`](../api/aiApiSpec.md) · [`aiApiSpec.md §5` 항목 7](../api/aiApiSpec.md)
- **분류**: 부분 확정
  - **계산 주체 — 확정됨**: 파생 지표(평가손익 등)는 **전부 AI가 계산한다**
    (`aiApiSpec.md:202` "파생 지표는 전부 AI 가 계산합니다(명세 10.1)"). 백엔드 `/internal/v1`은 원장
    원값(보유·현금·거래 이력)만 내려주고 계산하지 않는다
  - **필드·엔드포인트 — 대부분 확정됨**: `GET /internal/v1/portfolio`·`GET /internal/v1/trades`
    스키마로 구현됨(`aiApiSpec §4.1`)
  - **잔여 미정**: 입출금 이력·거래 수수료를 `/internal/v1`에 포함시킬지. `aiApiSpec §5` 항목 7이 이미
    `[S0-5]`로 태그하고 결정 주체를 "백엔드"로 지목해 뒀다
- **제안 기본값**: **MVP에서는 입출금·수수료를 포함하지 않는다.** AI는 보유·거래 원자료만으로 계산한다
  - **근거**: 수수료는 `featureSpec 1.1`이 이미 "미적용"으로 확정했으므로 애초에 왜곡 요인이 아니다(항상
    0). 입출금(충전)은 왜곡 가능성이 남지만, MVP 수익률 표시가 "종목별 평가손익·평가수익률"로 한정되고
    (`featureSpec 1.1`) 계좌 전체 수익률·자산 추이는 확장 범위로 빠져 있어(`featureSpec` 확장 표) 지금
    당장 급하지 않다
- **누가 막혀 있나**: AI의 계좌 레벨(포트폴리오 전체) 수익률·브리핑 정확도 — 종목별 지표만 쓰는 현재 MVP
  범위에서는 사실상 막힌 것이 없다
- **나중에 바꿀 위치**: `/internal/v1/portfolio`·`/internal/v1/trades` 응답 스키마(백엔드), AI
  `app/core/adapters.py`의 `BackendLedgerSource`
- **실측으로 갱신할 조건**: 실측이 아니라 스코프 문제다 — 포트폴리오 전체 수익률·자산 추이(확장 범위)가
  착수될 때 재검토한다

## S0-6 — 공시·뉴스 원천

- **원문**: [`featureSpec.md` S0-6](./featureSpec.md) ("한국투자증권 OpenAPI 1차 채택. 뉴스가 제목
  위주면 DART 병행 검토") · [`ai/docs/api-spec.md:24`](../../ai/docs/api-spec.md)
- **분류**: 이미 확정 + 구현됨 — **단, 원문과 다른 값으로.** `ai/docs/api-spec.md:24`가 데이터 원천을
  "KIS OpenAPI(시세) · pykrx(히스토리) · **DART(공시·재무)** · **NAVER API HUB(뉴스 검색 결과)** ·
  ECOS(거시)"로 명시하고, `ai/docs/seed-dataset.md`가 DART 기반 적재를 실측·검증까지 마쳤다(2026-08-20).
  즉 "KIS 1차, 안 되면 DART 병행 검토"가 아니라 **처음부터 공시=DART, 뉴스=NAVER API HUB로 직행**해 이미
  운영 중이다
- **이것은 정리 대상이 아니라 보고 대상이다**: `featureSpec.md`(공식 SSAFY 계승 문서)의 S0-6 행은 여전히
  "미정"·"한국투자증권 OpenAPI 1차"라고 적혀 있는데, 실제 구현은 이미 다른 원천으로 끝나 있다. 사서는
  이 값 충돌을 임의로 고치지 않는다 — `featureSpec.md`를 갱신할지는 그 문서의 판단이다
- **제안**: AI 구현을 그대로 ver2 결정으로 추인한다 — 공시 DART, 뉴스 NAVER API HUB. 이미 동작 중인 것을
  되돌릴 이유가 없다
- **누가 막혀 있나**: 아무도 (이미 구현되어 동작 중)
- **나중에 바꿀 위치**: `ai/docs/api-spec.md` 데이터 원천 표, `ai/app/ingest/*`
- **실측으로 갱신할 조건**: 이미 실측·운영 단계. 원천을 바꿀 이유(DART 일일 호출 한도, NAVER 검색 품질
  등)가 생기면 그때 재검토한다

## S0-7 — 시세·AI 장애 fallback

- **원문**: [`featureSpec.md` S0-7](./featureSpec.md) ("마지막 수신 가격 허용 범위, AI 캐시 응답") ·
  [`apiSpec §5.4`](../api/apiSpec.md)(`stale`) · [`apiSpec §10.4`](../api/apiSpec.md)(AI 에러 통과 규칙) ·
  [`ai/docs/api-spec.md` §2.2](../../ai/docs/api-spec.md)(`freshness_warnings`·`cached`)
- **분류**: 대부분 이미 확정 + 구현됨. 세 갈래로 나뉘던 것이 전부 답이 있다
  1. **시세 장애** (마지막 수신 가격 허용 범위) → `apiSpec §5.4`의 `stale` 필드 + 위 S0-3 제안(15초)으로
     확정
  2. **AI 장애** (백엔드가 AI 서버에 도달 못함) → `apiSpec §10.4`가 `AI_UPSTREAM_UNAVAILABLE`(502)·
     `AI_UPSTREAM_TIMEOUT`(504)으로 이미 백엔드 자체 장애와 구분해, 프론트가 AI 위젯만 죽이고 나머지
     화면(시세·주문)은 살리도록 확정했다
  3. **AI 내부 데이터 신선도** (공시·뉴스·거시 지표가 오래됐을 때의 "AI 캐시 응답") →
     `ai/docs/api-spec.md`의 응답 봉투가 이미 `freshness_warnings` 배열과 `cached` 필드를 갖고 있고,
     소스별 `threshold_seconds`로 경고를 낸다(예시: 뉴스 6시간)
- **잔여 미정**: `freshness_warnings`의 소스별 `threshold_seconds` 중 `price` 값 — 예시에는 `news`만
  있다
- **제안**: `price` 소스의 `threshold_seconds`는 S0-3 제안값과 **동일하게 15초**로 통일한다. 새 숫자를
  따로 만들 이유가 없다 — 시세가 15초 이상 지연되면 이미 `stale: true`로 화면에 드러나므로, AI 응답의
  신선도 경고도 같은 기준을 쓰는 편이 두 표시가 어긋나지 않는다
- **누가 막혀 있나**: 아무도. 설계·구현 모두 있고 남은 것은 수치 정렬뿐
- **나중에 바꿀 위치**: AI 서버 설정(freshness threshold 상수, AI 소유), `apiSpec §10.4` 에러 코드 표
  (백엔드 소유)
- **실측으로 갱신할 조건**: S0-3 값이 실측 후 바뀌면 `price` threshold도 같이 맞춘다

## 부록 A — `lab.ssafy.com` 링크에 대하여

`frontend/docs/contracts.md`·`frontend/docs/ia.md`·`frontend/docs/frontConvention.md`에 SSAFY GitLab
(`lab.ssafy.com/.../S15P21A101/-/issues/N`) 링크가 17건 있다. **죽은 링크는 아니다** — 그 서버는 살아
있을 수 있다. 다만 SSAFY 팀은 해산했고 ver2는 그 저장소에 접근·회신을 받을 수 없다.

이미 회신을 받아 "닫힘, 회신 있음"으로 표시된 이슈는 그 자체로 완결된 기록이라 문제가 없다. 위험한 것은
**"이슈 없음 (스프린트 0 결정)"이나 "회신 대기"로 남아 있는 항목**이다 — 예: `contracts.md` P9·P10·P11
(S0-2·S0-3·S0-4)은 애초에 GitLab 이슈조차 없이 "8/26 결정 회의"만 가리키고 있었다. 이 문서(위 S0-1~S0-7)
가 그 자리를 메운다.

`frontend/docs/**`는 프론트 소유라 사서는 본문을 직접 고치지 않는다. 프론트에게 넘길 제안: 각 파일 상단에
"`lab.ssafy.com` 링크는 SSAFY 팀 해산 전 기록이며 더 이상 회신이 오지 않는다" 한 줄을 추가하는 것.
