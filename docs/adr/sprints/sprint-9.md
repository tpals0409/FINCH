# Sprint 9 — 실가동과 계측

_날짜: 2026-09-08_

## 목표

**켜지 않은 채로는 아무것도 증명되지 않는다.** Sprint 8 은 값 넷을 클러스터에 넣고
`KIS_PRICE_ENABLED` 만 `false` 로 둔 채 닫혔고, ADR 에 그 이유를 적어놨다 — 조건부 빈은
조립되지 않으므로 스위치가 꺼진 채 파드가 뜨는 것은 값의 정합성을 증명하지 않는다.

그래서 이 스프린트의 목표는 세 줄이었다.

```
값 넷의 정합성    켠 직후 파드 Ready. 어긋나면 예외 로그가 아니라 CrashLoop 이다
Redis 적재        asOf 가 실제로 전진하는가
stale 전이        되는 것과 안 되는 것이 구분되는가
```

## 결정 사항

### D1. 스위치는 개장 전에 켠다

`KIS_PRICE_ENABLED=true` 한 줄(gitops `48958ff` #13)을 09:00 정규장 전에 올렸다.
켠 직후 파드 Ready 확인이 검증의 일부라고 Sprint 8 ADR 이 못박아뒀고, 장이 열린 뒤에
켜면 기동 실패와 수집 실패가 같은 시간대에 섞인다.

### D2. 장중 롤아웃은 "고칠 시간이 남아 있는가" 로 판단한다

하루에 backend 롤아웃을 세 번(#57 · #64 · #66) 감행했다. 판단 기준은 하나였다 —
**지금 넣으면 틀렸을 때 고칠 시간이 있고, 마감 뒤에 넣으면 확인할 방법이 없다.**
셋 다 `KisPriceCollector` 를 건드리지 않아 관측 중인 수집 경로와 독립이었고, 새 Pod 의
Ready 전이 시각부터 30초를 `stale` 관측의 제외 후보 구간으로 따로 기록했다.

기각한 대안은 "관측이 끝난 뒤 한 번에 머지" 였다. 그러면 #66(현재가 조회 API 연결)이
오늘 안 들어가고, **내일 09:00 핫셋 30종을 실제 시세 조회 경로로 확인할 수 없게 된다.**

### D3. `stale` 은 이벤트가 아니라 상태다 — 관측에 창이 없다

이 스프린트에서 가장 크게 틀린 프레이밍이고, 코드 세 줄이 그것을 뒤집었다.

```
application.yaml:95        stale-after: 15s          (finch-gitops 전체 오버라이드 0건)
PriceService.kt:56         stale = Duration.between(tick.asOf, now) > staleAfter
PriceCacheWriter.kt:16     "마지막 수신값은 stale 상태에서도 유지해야 하므로 TTL 을 두지 않는다"
```

`stale` 은 어딘가에 쓰이는 플래그가 아니라 **읽는 순간 계산하는 값**이다. 그리고 틱 키에
TTL 이 없고 `price` 도메인에 삭제 경로가 없으므로(grep 0건) 마지막 틱은 밤새 남는다.

따라서 수집기가 멈춘 15:30:03 이후 **다음 개장까지 언제 읽어도 `stale: true`** 다.
장 마감을 4분짜리 실험 장치로 설계한 것은 지연되는 로직과 지연을 판정하는 로직을
혼동한 결과였다.

### D4. 증거는 등급을 구분해 적는다

`stale: true` 를 "첫 실물 관측" 이라고 부르려다 Pico 가 정정했다. 실제 증거는 두 종류다.

```
live read      Redis GET price:005930 의 asOf · TTL          ← 실측
결정식 판정     배포 설정 15s + PriceService.kt:56 에 대입     ← 재현 가능한 코드 경로 판정
미실행         공개 API 응답 직접 호출 (JWT 필요)
```

**둘을 한 단어로 뭉치지 않는다.** 이 팀은 "초록불이 다른 커밋의 것이었다"(Sprint 8
인시던트 3)로 한 번 데였고, 그때와 같은 종류의 실수다 — 증거의 출처를 확인하지 않는 것.
토큰을 새로 발급해 방에 노출하지 않는 운영 경계를 지킨 결과이기도 하다.

### D5. 선행 조건은 스케줄을 기다리지 않고 오늘 확인한다

`#69`(전일 종가)의 선행 조건은 내부 API 가 non-empty 인 것이고, 그것을 채우는
`ingest.price_snapshots` 를 CronJob(07:30)에 올렸다. **내일 아침까지 기다릴 이유가 없었다.**
같은 이미지로 수동 Job 을 한 번 돌려 셋을 오늘 확정했다 — `KRX_API_KEY` 가 실제로 살아
있는지 · 적재가 되는지 · 내부 API 가 non-empty 인지.

키가 비어 있었다면 내일 07:30 에 CronJob 이 즉시 죽고 `#69` 가 통째로 밀렸을 것이다.

### D6. `ci.yml` 을 바꾸는 PR 은 낡은 초록불로 머지하지 않는다

`#72`(CI SSOT)의 초록불은 13:15 의 `758c4aa` 것이었고 그 뒤 master 에 10건이 들어갔다.
최신 master 위로 재배치해 `08e3cf1` 에서 CI 를 다시 받고 머지했다.

`#66` 도 같은 이유로 재배치했는데, base 변경만으로는 CI 이벤트가 생기지 않았다.
**SHA 를 인위적으로 바꾸지 않고** PR 을 닫았다 다시 열어 같은 HEAD 로 CI 를 돌렸다.

### D7. 원인을 특정할 수 없으면 "미상" 으로 적는다

`backend` Deployment 의 generation 10 에서 이미지가 아직 #57 이던 시점의 template 변경
필드를 사후 특정할 수 없었다(당시 manifest 없음). 배제할 수 있는 것은 다 배제했고
(#14 차트 변경 · HPA), 클러스터는 Synced/Healthy · restart 0 이라 **지금 해를 끼치고
있지 않다.** 추측으로 채우지 않고 "원인 미상 · 무해 관측" 으로 남긴다.

## 인시던트

1. **`stale` 관측을 4분짜리 마감 창으로 설계했다.** 장 마감(15:30)을 실험 장치로 쓴다고
   선언하고 Pico 를 15:29~15:33 샘플러에 묶었다. 실제로는 `stale` 이 읽는 시점 계산이고
   틱 키에 TTL 이 없어 **밤새 언제 읽어도 같은 답**이 나온다(D3). 창이라는 것이 없었다.
   지연되는 로직과 지연을 판정하는 로직을 혼동했다.

2. **어제 데이터로 되는 범위를 좁게 봤다.** `#69`(전일 종가)를 "내일 07:30 CronJob 이후"
   로 묶었지만 `price_snapshots.py:112` 가 `--date` 를 받고 5일 전까지 거슬러 최근
   거래일을 찾는다 — 오늘 한 번 돌리면 되는 것이었다. 캔들 backfill 도 마찬가지로
   `get_market_ohlcv_by_date` 는 키 없이 되고 실측 기록(30종 × 268거래일 · 8초)이 이미
   `seed-dataset.md` 에 있었다. **스냅샷 테이블의 제약을 캔들 backfill 에까지 확대 적용**
   했다. Leo 의 "어제 데이터 기준으로 하면 되는 거 아니야?" 로 풀렸다.

3. **"#64 가 오늘 마지막 backend 롤아웃" 이라고 단정했다가 뒤집었다.** 46분 뒤 #66 을
   머지해 세 번째 롤아웃을 만들었다. 판단 자체는 D2 대로 일관됐지만, 남은 큐를 보지 않고
   "마지막" 을 선언한 것이 성급했다. Pico 는 그 말을 기준으로 관측 계획을 세운다.

4. **증거 등급을 한 단어로 뭉갰다.** `asOf` 실측과 코드 결정식 판정을 합쳐 "첫 실물 관측"
   이라고 발행했다. Pico 가 범위를 정정했고 D4 로 기록 규칙을 세웠다.

5. **ADR 초안이 존재하지 않았다.** "초안은 다 썼습니다" 라고 방에 보고했지만 디스크
   어디에도 없었다 — 컨텍스트에만 있었고 세션이 끊기며 사라졌다. 종료 직전에 발견해
   다시 썼다. **파일로 쓰지 않은 산출물은 없는 것이다.**

6. **`005930` NETWORK_ERROR WARN 이 한 시간 넘게 섞였다.** 14:21:58 부터 15:29:55 까지
   5초 주기. 마지막 성공 tick 이 15:30:03(마지막 WARN 의 8초 뒤)이므로 **간헐적 실패**였고
   수집기는 장 마감까지 살아 있었다. 원인은 미규명 — Sprint 10 으로 넘긴다.

7. **로컬 테스트 56건 실패를 코드 실패로 읽을 뻔했다.** 종료 검증으로 `./gradlew clean

   메시지가 전부 `Could not find a valid Docker environment` — 컨테이너 런타임이 꺼져
   있어 Testcontainers 가 Postgres 를 못 띄운 것이었고 **코드 실패는 0건**이었다.

   다시 돌려 `BUILD SUCCESSFUL · 186 tests · 0 failures` 를 받았다. 오늘 세 번째로 나온
   같은 실패 모드다 — **관측이 안 맞으면 관측 환경부터 의심한다.**

## 발견

**핫셋 밖 종목은 정규장에도 거래가 막힌다.** `stale` 을 확인하다 찾았다.

```kotlin
// OrderService.kt:101-104 (apiSpec 7.2 순서) · latestPrice():216 도 같은 조건으로 예외
!isMarketOpen()  -> ORDER_MARKET_CLOSED
stock.suspended  -> ORDER_STOCK_SUSPENDED
price.stale || currentPrice == null || <= 0 -> ORDER_PRICE_UNAVAILABLE
```

`stale` 을 주문 거절 사유로 쓰는 것은 의도된 설계다 — 지연된 값으로 체결하면 사용자가
화면에서 본 가격과 다른 가격에 사고팔게 된다. 문제는 **핫셋 밖 종목이 `PriceRes.empty()`
이고 `empty()` 의 `stale` 이 `true`** 라는 점이다.

```
핫셋 안 (오늘 1종목)     주문 가능
핫셋 밖 (2,597종목)      ORDER_PRICE_UNAVAILABLE
```

오늘 정규장 동안 거래 가능 종목은 1개였다. 밤에는 `MARKET_CLOSED` 가 먼저 걸려 증상이
보이지 않는다. 그리고 최근 본 종목 기록(#78)이 없으므로, 사용자가 어떤 종목을 사려면
**먼저 관심 종목에 넣고 수집기가 집어갈 때까지 기다려야 한다.**

이것이 `#78` 의 선행 조건(처리량 실측)이 왜 강한 제약인지도 설명한다. 핫셋이 상한을
넘으면 `stale` 이 뜨고, `stale` 이 뜨면 **화면이 느려지는 게 아니라 거래가 멈춘다.**

## 교훈

- **시간에 묶인 것과 상태로 남는 것을 구분한다.** `stale` 을 마감 이벤트로 읽어 4분 창을
  만들었지만, 읽는 시점 계산 + TTL 없음 = 창이 없는 상태였다. "언제까지 관측해야 하나"
  를 묻기 전에 **그 값이 어떻게 만들어지는지**를 먼저 본다. 코드 세 줄이면 답이 나온다.
- **제약을 인접 항목에 확대 적용하지 않는다.** 스냅샷 테이블이 내일부터 쌓인다는 사실을
  캔들 backfill 에까지 옮겨 붙여 오늘 할 수 있는 일을 내일로 밀었다. 이슈 본문에는
  맞게 적어놓고 방에서는 뭉갰다.
- **증거를 등급으로 적는다.** live read 와 코드 결정식 판정은 다른 강도다. 한 단어로
  합치면 나중에 그 기록을 읽는 사람이 무엇이 실제로 관측됐는지 복원할 수 없다.
- **파일로 쓰지 않은 산출물은 없는 것이다.** "초안은 다 썼다" 고 보고한 것이 컨텍스트에만
  있었다. 보고할 만한 것은 보고 전에 디스크에 있어야 한다.
- **"마지막" 을 선언하기 전에 남은 큐를 본다.** 다른 사람이 그 말을 기준으로 계획을
  세운다. 확신이 없으면 "지금까지 예정된 마지막" 이라고 쓴다.
- **관측이 안 맞으면 관측 환경부터 의심한다.** Sprint 8 에서 HTTP 400 이 진단 `grep` 의
  버그였고 ArgoCD 드리프트가 잘못된 Application 이었다. 이번엔 테스트 56건 실패가 꺼진
  컨테이너 런타임이었다. 세 번 다 코드는 멀쩡했다. 그리고 세 번 다 **레포나 메모리에 답이
  이미 적혀 있었다.**
- **Sprint 8 의 CI 머지 레이스는 재발하지 않았다.** 13커밋 전부 CI·Images success 다.
  앞 PR 의 Images 가 끝나고 gitops 태그가 오른 것을 보고 다음을 머지하는 규칙이 실제로
  작동했다. 교훈이 규칙이 되면 인시던트가 안 생긴다.
