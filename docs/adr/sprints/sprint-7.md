# Sprint 7 — 화면과 배포, 그리고 팀

_날짜: 2026-09-07_

## 목표

계획은 하나였다 — **`RoutePlaceholder` 9개를 채운다.** 배포와 KIS 는 사용자 입력 대기라
거기 안 걸리게 MSW 목 위에서 화면을 짠다는 것이 Sprint 6 이 넘긴 전제였다.

그 전제가 스프린트 중에 무너졌다. 인증서와 카카오 키가 놓이면서 **배포가 실제로 됐고**,
서버에서 KIS 가 뚫리자 시세 수집이 범위 안으로 들어왔다.

## 결정 사항

### D1. 파트 에이전트를 Buzz 에 올린다. Fin 이 오케스트레이션한다

`.claude/agents/` 에 있던 역할 정의 6종 중 셋(backend·frontend·ai)을 Buzz 에이전트로 만들었다.
**본문을 새로 쓰지 않고 기존 파일을 그대로 썼다** — 레포에 이미 있는 것을 다시 지어내면
두 벌이 갈린다.

에이전트를 붙이기 전에 `gh issue list` 가 0건인 것을 확인했다. 큐가 빈 상태로 에이전트를
넣으면 "뭘 할까요" 메시지만 늘어난다. 이슈(#46 #47)를 먼저 끊고 배분했다.

### D2. 팀 규약의 SSOT 는 레포다. 로컬 nest 가 아니다

규약을 Fin 의 nest(`~/.buzz/.agents/skills/`)에 두었더니 Pico 에게 닿지 않았다.
Pico 가 실측으로 짚었다 — 그 서버에는 그 경로가 없다.

이 기계의 셋은 nest 를 공유하지만 Pico 는 다른 서버다. **레포가 환경을 넘는 유일한
공유 지점이라** 원본을 `.claude/skills/finch-team/SKILL.md` 로 옮기고 nest 는 심링크로 걸었다.
`docs/ops/pico.md` 가 이미 같은 이유로 레포에 있다.

### D3. 메시지 컨벤션은 접두 태그. 고정 섹션 템플릿이 아니다

`[완료] [차단] [요청] [질문] [결정] [상태]` 여섯 개로 시작한다.

고정 섹션(무엇을/근거/다음)을 안 고른 이유는 **왕복의 절반이 한두 줄**이기 때문이다.
거기에 헤더 세 개를 얹으면 가독성이 더 나빠진다. Pico 가 제안한 칸 이름
(`결과/영향` `근거` `다음` `주의`)은 어휘로 채택하되 필수로 만들지 않았다.

실제 문제는 형식이 아니라 **길이**였다. 그래서 "15줄 넘으면 캔버스나 PR 본문으로 빼고
링크만" 을 같이 걸었다. 코드 리뷰 본문은 채널이 아니라 PR 코멘트에 쓴다.

### D4. 스프린트의 정체성을 Buzz 스레드로 옮긴다

최상위 메시지 하나가 스프린트이고 그 event id 가 스프린트 id, 아래 스레드가 진행 기록이다.
`/sprint-open` `/sprint-close` 는 유지하고 두 단계만 붙였다.

근거는 이 스프린트 안에서 조사한 결과다. `sprint-window.md` 는 **한 세션의 작업 기억**인데
에이전트가 넷으로 늘었다. 어긋남 3건이 나왔고 전부 메모리·수동 표기에서 나왔다 —
ADR 은 하나도 안 틀렸다.

`sprint-window.md` 를 없애지는 않았다. `status` 가드가 중단 복구를 실제로 해준다
(`idle` 전환이 마지막인 설계). **서사는 스레드가, 포인터는 윈도우가** 든다.

### D5. KIS 수집은 정규장에만 돈다. 공휴일은 넣지 않는다

`@Scheduled(fixedDelay 3s)` 가 24시간 돌고 있었다. featureSpec §7.4 의 거래 시간은
`09:00~15:30` 이다. 하루 6.5시간인데 24시간 돌면 KIS 일일 쿼터를 밤새 태우고, 마감 후에도
`asOf` 를 현재 시각으로 재스탬프해 `stale` 이 영원히 false 가 된다.

**공휴일은 의도적으로 안 넣었다.** 유지되는 KRX 휴장일 달력이 필요한데 그건 이 PR 이
감당할 일이 아니다. 연 15일 안팎 남는 것을 알고 두기로 했고, 코드와 `backConvention.md`
양쪽에 그 판단을 적었다 — 다음 사람이 "왜 공휴일은 없지" 하고 달력을 만들기 전에.

### D6. AI 검색에 HNSW 를 채택한다

무인덱스 실측 후 판정한다는 것이 Sprint 6 이 남긴 조건이었다. 채택 기준을 **수치를 보기 전에**
고정했다 — Recall@5 `1.000` 유지 · 중앙값과 p95 모두 감소 · p95 30% 이상 감소.

셋 다 충족했다. `IVFFlat` 대신 HNSW 를 고른 이유는 이 규모(10,198행)에서 목록 수·probe 튜닝과
학습이 필요 없고 증분 적재에 강해서다.

### D7. `/dev/shm` 을 늘린다. 마이그레이션에서 병렬 빌드를 끄지 않는다

인덱스 빌드가 죽은 뒤 두 갈래가 있었다. 마이그레이션에 `max_parallel_maintenance_workers = 0`
을 넣는 우회(인프라 변경 0)와, GitOps 에서 `/dev/shm` 을 tmpfs 로 늘리는 길이다.

**처음에는 우회를 권했고 그 판단이 틀렸다.** 두 가지를 잘못 봤다.

1. tmpfs `sizeLimit` 을 예약으로 계산했다. 그건 **상한**이고 실제로 쓴 만큼만 컨테이너
   메모리에 잡힌다. "512Mi 를 떼면 postgres 몫이 512Mi 준다"는 틀린 문장이었다
2. 우회는 **이 마이그레이션 하나에만** 듣는다. 64Mi 기본값은 다음 병렬 인덱스 빌드·병렬
   쿼리에서 같은 자리에 다시 걸린다

원인을 고치는 쪽으로 갔다.

### D8. ArgoCD 앱 이름을 바꾼다. `prune: true` 로 바꾸지 않는다

`platform-namespaces` 가 계속 OutOfSync 였다. 원인은 git 이 아니라 **이름 충돌**이었다 —
PinLog 가 같은 클러스터·같은 `argocd` 네임스페이스에서 그 이름을 먼저 썼고, `monitoring`
네임스페이스에 추적 마커가 남아 있었다.

```
argocd.argoproj.io/tracking-id: platform-namespaces:/Namespace:pinlog-prod/monitoring
```

`prune: true` 로 바꾸면 Argo 가 PinLog 의 Prometheus·Grafana·Loki 를 실제로 지운다.
앱에 달린 `prune: false   # 네임스페이스 삭제는 데이터 유실이다` 주석이 정확히 이 사고를
막으려고 있었다. 클러스터에서 마커를 지우는 것도 아니다 — **저장소에서 고친다.**

`finch-prod` 가 안 지워지는 근거를 먼저 확인했다: 이 Application 에는
`resources-finalizer.argocd.argoproj.io` 가 없고, finalizer 없는 Application 삭제는 관리
리소스를 **고아로 만들 뿐 삭제하지 않는다.** 배포 후 `creationTimestamp` 가 그대로인 것으로
확인됐다.

### D9. 위키는 파생물이다. 여섯 번째 저장소를 만들지 않는다

LLM Wiki(karpathy) 적용 요청을 받고 3층 구조를 우리 것에 대보니
**`.claude/agents/librarian.md` 가 이미 그 패턴의 FINCH 판**이었다. 원문보다 엄격하다.

> 원본이 진실이고 위키는 지도다. 값을 복사하지 않는다.
> 판단 기준: 원본을 고쳤을 때 위키도 고쳐야 한다면 그 위키는 잘못 쓴 것이다.

없는 것은 `docs/wiki/` 디렉터리와, 사서가 Buzz 에이전트가 아니라는 것 둘뿐이었다.
새로 설계하지 않고 있는 것을 쓴다.

## 인시던트

1. **ArgoCD 앱 이름이 PinLog 와 겹쳐 남의 `monitoring` 네임스페이스를 상속했다**:
   GitOps 뼈대를 옮기면서 `platform-namespaces` 라는 **이름까지** 가져왔다. 같은 클러스터,
   같은 `argocd` 네임스페이스라 마커가 그대로 상속됐다. 실패 모드 —
   **구조를 옮길 때 이름도 옮기면 남의 소유권을 물려받는다.**

2. **`maintenance_work_mem` 을 올리면서 그 메모리가 어디서 나오는지 안 봤다**:
   startupProbe 150초가 걱정돼 256MB 를 권했다. 컨테이너 limit(1Gi)만 확인하고
   `/dev/shm`(쿠버네티스 기본 64Mi)은 보지 않았다. pgvector 병렬 빌드가 253Mi DSM 세그먼트를
   요구했고 프로덕션 롤아웃이 CrashLoopBackOff 로 죽었다. 실패 모드 —
   **파라미터를 올릴 때 그 자원의 출처를 확인하지 않았다.**

3. **`sizeLimit` 을 예약으로 오해해 옳은 해법을 한 번 막았다**:
   Pico 의 tmpfs 제안을 "1Gi 중 512Mi 를 떼면 postgres 몫이 준다"는 근거로 보류시켰다.
   `sizeLimit` 은 상한이고 tmpfs 는 쓴 만큼만 잡힌다. 실패 모드 —
   **상한과 예약을 구분하지 못하면 맞는 답을 거부한다.**

4. **수집기가 24시간 돌게 짜여 있었다**: 리뷰에서 잡았다. 장 운영시간 게이트가 없어 KIS
   쿼터를 밤새 태우고 마감 후 `stale` 이 영원히 false 가 될 상태였다. 주말도 안 막혀 있었다.
   실패 모드 — **스케줄러를 짤 때 도메인의 영업시간을 안 봤다.**

5. **표본 8개에서 p95 가 사실상 max 였다**: 리뷰에서 잡았다. `ceil(8×0.95)−1 = 7` 이라
   정렬 마지막 값이고, 그 값이 될 가능성이 가장 높은 것은 커넥션 셋업을 뒤집어쓰는 첫 질의다.
   워밍업 1회 버리고 5회 반복(n=40)으로 고쳤다. 실패 모드 —
   **표본 수를 보지 않고 백분위를 쓰면 잡음을 지표로 삼는다.**

6. **멘션이 남의 작업을 끊었다**: 실측하니 이벤트 99건에 지목 126회였고 **Fin 이 26건으로
   최다**였다. 접수 확인("확인했습니다" "기록했습니다")이 상당수였다. 실패 모드 —
   **알림이 공짜라고 생각하면 남의 진행 중인 작업을 끊는다.**

7. **"셋을 부르지 않았습니다"라고 쓰면서 셋을 깨웠다**: `--mention` 은 Leo 하나만 줬는데
   본문의 `@Finch-Back @Finch-Front @Finch-AI` 를 CLI 가 멤버 이름과 대조해 수신자로 넣었다.
   응답 JSON 의 `mention_pubkeys` 에 넷이 찍혀 있었다. 실패 모드 —
   **표시용으로 쓴 이름이 실제 알림이 된다.**

8. **규칙끼리 서로를 어겼다**: Pico 리뷰가 잡았다. "산문에 숫자를 섞지 않는다"가 바로 위
   접두 태그 예시(`/dev/shm 64Mi`)를 금지했고, "명령과 출력을 그대로 붙인다"가 15줄 상한과
   충돌했다. 실패 모드 — **규칙을 여러 절에 나눠 쓰면 서로를 모른다.**

9. **채널 보고와 PR 내용이 갈렸다**: "86줄 → 120줄"이라 보고한 뒤 파일을 더 고쳤고 PR 은
   171줄이었다. Pico 가 "PR 본문이 아니라 diff 를 기준으로 봐야 한다"고 지적했다. 실패 모드 —
   **보고 시점과 커밋 시점이 다르면 숫자가 낡는다.**

10. **할 수 있는 일이 남았는데 질문으로 턴을 닫아 두 번 멈췄다**: Fin 이 "무슨 작업을 할까요"로
    턴을 닫은 시각에 Pico 는 실행 가능한 요청을 보내놓고 답을 기다렸다. 실패 모드 —
    **물어봐야 할 것과 그냥 하면 되는 것을 안 갈랐다.**

## 교훈

- **이름은 소유권 마커다.** 구조를 옮길 때 이름까지 옮기면 남의 리소스를 상속한다. 같은 사고가
  한 스프린트에 두 번 났다 — ArgoCD 앱 이름과, 같은 방에 `Fin` 이 둘이라 멘션이 모호했던 것.
  **같은 공간에 같은 이름을 두 개 두지 않는다.**

- **파라미터를 올릴 때 그 자원이 어디서 나오는지 먼저 본다.** `maintenance_work_mem` 을 올리면서
  컨테이너 limit 만 보고 `/dev/shm` 을 안 봐서 프로덕션이 죽었다. **한도를 올린다는 것은 어딘가에서
  꺼내 온다는 뜻이고, 그 어딘가를 확인하지 않으면 다른 한도에 부딪힌다.**

- **상한과 예약은 다르다.** `sizeLimit` 을 예약으로 계산해 맞는 해법을 한 번 막았다.
  단위와 의미를 확인하는 비용이 틀린 판단을 되돌리는 비용보다 항상 싸다.

- **측정값은 나눠서 본다.** 검색 지연 320ms 중 실제 인덱스 스캔은 3.174ms 였다. 전체 수치만 보면
  엉뚱한 데를 튜닝한다. **인덱스를 채택한 것보다 "여기를 더 파지 말라"가 이 작업의 산출물이다.**

- **불변으로 굳힌 것은 안 틀리고 손으로 고치는 것은 틀린다.** 스프린트 방식 조사에서 어긋남
  3건이 나왔는데 전부 메모리·수동 표기에서 나왔고 ADR 은 하나도 안 틀렸다. 에이전트가 넷으로
  늘면 이 격차가 커진다.

- **커밋만으로는 인시던트가 안 보인다.** `sprint-6` ADR 의 인시던트 5건 중 커밋 메시지에 남은
  것은 하나도 없다. 이번 `/dev/shm` 64Mi 도 어떤 커밋에도 없고 채널 왕복에만 있다.
  **그래서 스프린트 회고가 스레드를 읽어야 한다.**

- **알림은 공짜가 아니다.** 멘션 하나가 상대의 진행 중인 작업을 끊는다. 지목 126회 중 상당수가
  접수 확인이었다. **보고할 게 생겼을 때 보내고, 받았다는 말은 보내지 않는다.**

- **리뷰가 실제로 잡았다.** 24시간 수집, n=8 의 p95, 0원 통과, 규칙 충돌 — 전부 머지 전에
  잡혔고 빌드도 테스트도 잡지 못하는 것들이었다. **다른 눈으로 한 번 더 읽는 값이 여기 있다.**
