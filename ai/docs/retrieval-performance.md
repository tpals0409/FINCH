# 검색 지연 측정과 벡터 인덱스 기준

이 문서는 코퍼스 검색 지연을 재는 절차와 인덱스 도입 근거를 기록한다.

## 측정 범위

- 평가셋: `eval/retrieval.yaml` v3, 8질의(정답 평가 7건 + 오탐 관찰 1건)
- 검색 범위: `search_with_vector` 호출만 측정한다. 질의 임베딩과 LLM 생성은 제외한다.
- 조건: `top_k=5`, 전체 질의 세트 1회 워밍업은 표본에서 제외한다.
- 표본: 전체 질의 세트를 5회 반복한 40건
- 요약: 중앙값과 nearest-rank p95, 질의별 중앙값
- 품질 게이트: `Recall@5 >= 0.75`

실행 명령은 다음과 같다.

```bash
python -m eval.run --retrieval --top-k 5 --repeat 5
```

## 판정 기준의 한계

첫 운영 측정 전에 판정 기준을 공개하거나 커밋하지 않았다. 측정 뒤 검토 과정에서 제시한
중앙값 100ms·p95 250ms에는 인용할 외부 근거나 기존 프로젝트 결정도 없다. 따라서 이
수치를 사전 기준이나 HNSW 도입의 독립 근거로 사용하지 않는다.

`ai_responses`의 비캐시 사용자 대면 응답 표본도 0건이라 검색이 전체 응답에서 차지하는
비율을 계산하지 못했다. HNSW는 무인덱스 검색의 관측 절대값을 줄일 수 있는지 확인하는
비교 후보이며, 아직 최종 채택 결정이 아니다.

인덱스 후 결과를 보기 전에 다음 채택 기준을 고정한다. 이 값은 외부 표준이 아니라,
근사 검색의 리콜 위험과 인덱스 운영 비용을 감수할 만큼 변화가 커야 한다는 프로젝트 내부
판단이다.

1. 현재 품질인 `Recall@5 = 1.000 (7/7)`을 그대로 유지한다.
2. 무인덱스 대비 중앙값과 p95가 모두 줄고, p95는 30% 이상 줄어든다.

검색이 전체 응답 시간에서 차지하는 몫은 같은 운영 환경의 `ai_responses.latency_ms`와
함께 기록한다. 지금은 표본이 없으므로 비율 판정을 보류하고, 실제 비캐시 응답이 쌓이면
보완한다.

## 운영 측정 결과

2026-09-07 15:31:02 KST 복원본은 `documents=219`, `document_chunks=10,198`,
`index_daily=271`, `instruments=2,598`이다. 평가셋의 정답 제목 부분 문자열 7개도
모두 1건 이상 존재했다. `absent-launch`는 정답이 없어야 하는 관찰 항목이라 이 대조에서
제외했다.

### 인덱스 전

운영 AI Pod에서 커밋 `4c06e6f`의 평가 실행기를 stdin으로 한 번 실행했다. 배포 이미지와
Pod 파일은 바꾸지 않았다.

| 항목 | 결과 |
| --- | ---: |
| Recall@5 | 1.000 (7/7) |
| 검색 지연 중앙값 | 387.9ms |
| 검색 지연 p95 | 587.7ms |
| 표본 | 40건 |

중앙값 387.9ms·p95 587.7ms라는 절대값을 관측해 인덱스 후보 비교를 시작한다. 위에서
기록했듯 전체 응답 대비 비율은 알 수 없고, 절대 임계도 사전에 정하지 않았다.

같은 시점의 `ai_responses`에서 `latency_ms IS NOT NULL AND cached=false`인 행은 0건이었다.
따라서 검색이 전체 사용자 대면 AI 응답 시간에서 차지하는 비율은 아직 계산할 수 없다.
실제 비캐시 응답 표본이 쌓인 뒤 이 값을 보완한다.

### 인덱스 설정

코사인 거리 `vector_cosine_ops`의 HNSW를 사용한다. 현재 10,198행 규모에서는 별도 학습과
목록 수·probe 튜닝이 필요한 IVFFlat보다 운영과 재현이 단순하고, 이후 문서가 증분 적재돼도
인덱스를 다시 학습할 필요가 없다. `m=16`, `ef_construction=64`로 시작하며 검색 시 기본
`ef_search=40`을 사용한다.

HNSW는 근사 검색이고 필터가 있는 질의에서 후보가 줄 수 있다. 따라서 같은 40개 표본의
지연뿐 아니라 `Recall@5 >= 0.75`가 유지되는지 함께 확인한 뒤 채택 여부를 확정한다.

### 인덱스 후

GitOps에서 AI PostgreSQL의 `/dev/shm`을 메모리 기반 `emptyDir` 512Mi로 구성한 뒤
Alembic 리비전 `b4e8c7a2d1f6`과 HNSW 인덱스 생성을 확인했다. 처음에는 컨테이너 기본
`/dev/shm` 64Mi에서 약 253Mi의 shared-memory segment를 만들지 못해 마이그레이션이
롤백됐다. 512Mi 적용 뒤 새 PostgreSQL 컨테이너의 재시작 횟수는 0이었고 OOM 없이
AI Pod가 기동했다.

재측정 전에 evaluator와 같은 코사인 거리 정렬 질의를
`EXPLAIN (ANALYZE, BUFFERS)`로 확인했다. 실행 계획은
`Index Scan using ix_document_chunks_embedding_hnsw`였고 대표 실행 시간은 3.174ms였다.
따라서 인덱스가 존재하기만 하고 검색에는 쓰이지 않는 경우를 배제했다.

이후 인덱스 전과 같은 워밍업·반복 조건으로 측정했다.

| 항목 | 인덱스 전 | 인덱스 후 | 변화 |
| --- | ---: | ---: | ---: |
| Recall@5 | 1.000 (7/7) | 1.000 (35/35) | 유지 |
| 검색 지연 중앙값 | 387.9ms | 319.761ms | 17.6% 감소 |
| 검색 지연 p95 | 587.7ms | 399.483ms | 32.0% 감소 |
| 표본 | 40건 | 40건 | 동일 |

인덱스 후 35/35는 정답 평가 7질의를 5회씩 실행한 결과다. 정답이 없어야 하는
`absent-launch` 5회는 이전과 동일하게 관찰 전용이며 Recall 분모에서 제외했다. 실행
오류는 0건이었다.

Recall 1.000을 유지했고 중앙값과 p95가 모두 줄었으며, p95가 30% 이상 감소해 고정한
채택 기준을 모두 충족했다. 따라서 이 코퍼스와 검색 조건에서는 HNSW 인덱스를 채택한다.
전체 AI 응답 대비 검색 비율은 비캐시 응답 표본이 쌓인 뒤 별도로 보완한다.

대표 `EXPLAIN ANALYZE`의 서버 측 인덱스 스캔은 3.174ms였지만, 애플리케이션에서 잰
인덱스 후 검색 구간 중앙값은 319.761ms였다. 두 값의 차이는 약 316.6ms로, 대표 스캔
시간은 애플리케이션 측 구간의 약 1%다. 두 값은 같은 표본의 구간별 추적 결과가 아니므로
차이 전부를 특정 원인에 귀속할 수는 없다. 이 구간에는 DB 왕복, 커넥션·세션 획득,
드라이버 처리, 조인과 결과 변환 등이 함께 들어갈 수 있다.

따라서 다음 지연 개선은 `m`이나 `ef_construction`을 더 조정하는 작업보다 이 약 316.6ms를
구간별로 계측하는 데서 시작한다. 다만 `ai_responses`의 비캐시 응답 표본이 0건인 현재는
전체 응답에서 이 비용이 차지하는 비율을 알 수 없으므로, 사용자 대면 지연 최적화의 우선순위는
표본이 쌓인 뒤 정한다.

## 검색 내부 구간 계측

2026-09-08에 평가 실행기가 `search_with_vector` 한 호출을 다음 구간으로 나눠 같은
8질의 × 5회 표본에서 측정하도록 보강했다.

- 세션·커넥션 획득
- DB 왕복·실행
- 결과 변환
- 세션 반환
- RRF 융합
- 위 구간에 포함되지 않은 파이썬 처리

로컬 공유 PostgreSQL에서 운영 복원본과 같은 `documents=219`,
`document_chunks=10,198` 및 HNSW 인덱스가 있는 상태로 측정한 결과다.

| 구간 | 중앙값 | p95 |
| --- | ---: | ---: |
| 검색 전체 | 60.0ms | 71.5ms |
| 세션·커넥션 획득 합계 | 2.5ms | 2.9ms |
| DB 왕복·실행 합계 | 53.5ms | 65.9ms |
| 결과 변환 합계 | 0.1ms | 0.1ms |
| 세션 반환 합계 | 1.1ms | 1.4ms |
| RRF 융합 | 0.5ms | 0.8ms |
| 그 밖의 파이썬 구간 | 2.0ms | 2.5ms |

DB 실행을 경로별로 나누면 밀집 벡터 검색은 중앙값 2.5ms, 제목 검색은 1.9ms,
어휘 검색은 48.7ms였다. 로컬 표본에서는 DB 실행이 검색 전체 중앙값의 약 89%이고,
어휘 검색이 그 대부분을 차지했다. Recall@5는 `1.000 (7/7)`을 유지했다.

이 값은 앞의 운영 측정 319.761ms와 같은 코퍼스·질의지만 같은 실행 환경의 표본은 아니다.
따라서 운영에서 관측한 약 316.6ms를 어휘 검색 하나에 귀속하지 않는다. 다음 최적화 후보는
어휘 검색의 실행 계획과 인덱스 사용 여부이며, 운영 우선순위는 전체 응답 지연 기록과 운영
환경에서 같은 구간 계측을 확보한 뒤 확정한다.

## 전체 AI 응답 지연 기록

`ai_responses.latency_ms`가 트래픽만으로 채워질 것이라는 전제도 틀렸다. 2026-09-08
운영 집계에서 전체 2행·비캐시 2행이 있었지만 `latency_ms IS NOT NULL`은 0행이었다.
라우트의 `record()` 호출부가 이 값을 한 곳도 넘기지 않았기 때문이다. 이후 HTTP 미들웨어가
요청 시작점을 열고 `record()`가 응답 로그 커밋 직전까지의 경과 시간을 자동으로 저장한다.
따라서 새 AI 라우트가 추가돼도 `record()`를 쓰는 한 별도 타이머를 빠뜨리지 않는다.

이 값은 AI 애플리케이션이 요청을 받은 뒤 응답 봉투를 완성하기까지의 시간이다. 응답 로그 자체의
DB 커밋, JSON 직렬화, 백엔드 중계와 프론트까지의 네트워크 시간은 포함하지 않는다. 배포 뒤
비캐시 응답을 의도적으로 만들어야 전체 응답 대비 검색 비율을 계산할 수 있다.

## 운영 환경 구간 재측정 절차

로컬 60.0ms와 운영 319.761ms의 차이를 같은 환경에서 가르기 위해, 검색 코드를 고치기 전에
운영 AI Pod에서 기존 8질의·`top_k=5`·5회 반복을 그대로 실행한다. 전체 질의 1회 워밍업은
이전처럼 40개 측정 표본에서 제외한다. 실행 전 코퍼스가 기존 기준
`219|10198|271|2598`와 다르면 측정하지 않는다.

Pico는 최신 FINCH 체크아웃의 `ai/`에서 아래 명령을 실행한다. 스크립트는 Ready인 AI Pod가
하나인지와 코퍼스 건수를 먼저 확인한다. 평가 파일만 Pod의 `/tmp`에 넣고 끝나면 지우므로
배포 이미지와 애플리케이션 파일은 바뀌지 않는다. 토큰·DB URL은 읽거나 출력하지 않는다.

```bash
./scripts/run_operational_retrieval_eval.sh
```

표준 출력은 Recall@5, 전체 검색과 세션 획득·DB 실행·결과 변환·세션 반환·RRF의 중앙값과
nearest-rank p95, 그리고 dense·title·lexical DB 실행을 보여준다. `$OUT_BASE.json`은
40개 각각의 `case_id`·반복 번호·전체 ms·구간별 ms·경로별 ms를 보존한다. 같은 파일의
`summary`는 그 원자료에서 계산한 중앙값과 p95이고, `environment_id`는 Pod·이미지 태그·
이미지 digest·평가 코드 HEAD를 묶는다. `dataset.sha256`으로 질의 세트까지 대조한다.
