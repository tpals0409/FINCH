# 검색 지연 측정과 벡터 인덱스 기준

이 문서는 코퍼스 검색 지연을 재는 절차와 인덱스 도입 근거를 기록한다.

## 측정 범위

- 평가셋: `eval/retrieval.yaml` v3, 8질의(정답 평가 7건 + 오탐 관찰 1건)
- 검색 범위: `search_with_vector` 호출만 측정한다. 질의 임베딩과 LLM 생성은 제외한다.
- 조건: `top_k=5`, 전체 질의 세트 1회 워밍업은 표본에서 제외한다.
- 표본: 전체 질의 세트를 5회 반복한 40건
- 요약: 중앙값과 nearest-rank p95, 질의별 중앙값
- 품질 게이트: `Recall@5 >= 0.75`

실행 명령은 다음과 같다.

```bash
python -m eval.run --retrieval --top-k 5 --repeat 5
```

## 판정 기준의 한계

첫 운영 측정 전에 판정 기준을 공개하거나 커밋하지 않았다. 측정 뒤 검토 과정에서 제시한
중앙값 100ms·p95 250ms에는 인용할 외부 근거나 기존 프로젝트 결정도 없다. 따라서 이
수치를 사전 기준이나 HNSW 도입의 독립 근거로 사용하지 않는다.

`ai_responses`의 비캐시 사용자 대면 응답 표본도 0건이라 검색이 전체 응답에서 차지하는
비율을 계산하지 못했다. HNSW는 무인덱스 검색의 관측 절대값을 줄일 수 있는지 확인하는
비교 후보이며, 아직 최종 채택 결정이 아니다.

인덱스 후 결과를 보기 전에 다음 채택 기준을 고정한다. 이 값은 외부 표준이 아니라,
근사 검색의 리콜 위험과 인덱스 운영 비용을 감수할 만큼 변화가 커야 한다는 프로젝트 내부
판단이다.

1. 현재 품질인 `Recall@5 = 1.000 (7/7)`을 그대로 유지한다.
2. 무인덱스 대비 중앙값과 p95가 모두 줄고, p95는 30% 이상 줄어든다.

검색이 전체 응답 시간에서 차지하는 몫은 같은 운영 환경의 `ai_responses.latency_ms`와
함께 기록한다. 지금은 표본이 없으므로 비율 판정을 보류하고, 실제 비캐시 응답이 쌓이면
보완한다.

제외했다.

### 인덱스 전

운영 AI Pod에서 커밋 `4c06e6f`의 평가 실행기를 stdin으로 한 번 실행했다. 배포 이미지와
Pod 파일은 바꾸지 않았다.

| 항목 | 결과 |
| --- | ---: |
| Recall@5 | 1.000 (7/7) |
| 검색 지연 중앙값 | 387.9ms |
| 검색 지연 p95 | 587.7ms |
| 표본 | 40건 |

중앙값 387.9ms·p95 587.7ms라는 절대값을 관측해 인덱스 후보 비교를 시작한다. 위에서
기록했듯 전체 응답 대비 비율은 알 수 없고, 절대 임계도 사전에 정하지 않았다.

같은 시점의 `ai_responses`에서 `latency_ms IS NOT NULL AND cached=false`인 행은 0건이었다.
따라서 검색이 전체 사용자 대면 AI 응답 시간에서 차지하는 비율은 아직 계산할 수 없다.
실제 비캐시 응답 표본이 쌓인 뒤 이 값을 보완한다.

### 인덱스 후보

코사인 거리 `vector_cosine_ops`의 HNSW를 사용한다. 현재 10,198행 규모에서는 별도 학습과
목록 수·probe 튜닝이 필요한 IVFFlat보다 운영과 재현이 단순하고, 이후 문서가 증분 적재돼도
인덱스를 다시 학습할 필요가 없다. `m=16`, `ef_construction=64`로 시작하며 검색 시 기본
`ef_search=40`을 사용한다.

HNSW는 근사 검색이고 필터가 있는 질의에서 후보가 줄 수 있다. 따라서 같은 40개 표본의
지연뿐 아니라 `Recall@5 >= 0.75`가 유지되는지 함께 확인한 뒤 채택 여부를 확정한다.
