엔드포인트화면이번 스프린트의 제약
GET /account 주식 잔고 요약 (아트보드 1·2) evaluationAmount 가 항상 0 이다. 보유가 없어서가 아니라 holding·price 도메인이 아직 없어서다. 따라서 totalAsset 은 cashBalance 와 같다. 보유 종목 목록(명세 9.2)은 범위 밖 — "보유 없음" 이 이 스프린트의 정상 화면이다.
GET /deposits/limit
POST /deposits		 충전 플로우 (3~6) · 에러 (7~9) 한도 수치는 화면이 계산하지 않고 응답의 perRequestLimit·cumulativeLimit·remainingAmount 를 그대로 쓴다. 충전 취소 API 는 존재하지 않는다 — 확인 화면에 "충전은 취소할 수 없습니다" 를 고정 노출한다 (명세 3.2).
GET /transactions 매매 내역 (10~14) 필터는 ALL·BUY·SELL·DEPOSIT 넷이고 화면 이름은 전체·매수·매도·충전 이다. 주문이 없으므로 매수·매도 탭은 항상 빈 결과다. type=ALL 은 INITIAL_GRANT 1건이 항상 있어 절대 비지 않는다.
화면 문구는 서버가 완성해서 내려준다 (apiSpec 1.3). 이 캔버스의 에러 문구는 새로 만든 것이 아니라 DepositErrorCode.kt·GeneralErrorCode.kt 의 message 를 그대로 옮긴 것이다. 화면마다 문구를 다시 만들지 않는다.
  • DEPOSIT_AMOUNT_INVALID · 400 — 충전 금액은 1원 이상이어야 합니다 → 아트보드 7
  • DEPOSIT_PER_REQUEST_LIMIT_EXCEEDED · 409 — 1회 충전 한도는 1,000만 원입니다 → 아트보드 7
  • DEPOSIT_LIMIT_EXCEEDED · 409 — 누적 충전 한도(1억 원)를 초과했습니다 → 아트보드 8, detail.remainingAmount 동반
  • IDEMPOTENCY_IN_PROGRESS · 409 — 같은 요청을 처리하고 있습니다. 잠시 후 다시 시도해 주세요 → 아트보드 9
이번 스프린트에 나오지 않는 행 형태 — 그리지 않았다. 명세 8장이 정의한 체결 건 행(일시·종목명·구분·체결가·수량·체결 금액, 매도는 realizedProfit·realizedProfitRate 추가)은 주문 도메인이 생긴 뒤에 그린다. 지금 그리면 시세·수익률 색을 쓸 자리가 생기고, 그건 이 스프린트가 내려주지 않는 값이다. GET /transactions 응답의 stockCode·stockName· price·quantity·realizedProfit·realizedProfitRate 가 충전·초기 지급 행에서 전부 null 인 것이 행 형태가 둘로 갈리는 이유다.
토큰을 새로 만들지 않았다. 이 캔버스의 모든 색·반경·그림자·타이포는 기존 역할 토큰으로 해결된다. 판단이 들어간 자리는 셋이다.
  • 위험·에러 알림에 등락 적색을 쓰지 않는다. bg-critical-weak 면 + fg-critical(잉크) bold + 아이콘. 적색이면 "떨어졌다" 로 오독된다 (finch-seed §4).
  • 충전·초기 지급 금액에 up/down 색을 쓰지 않는다. 유입이지만 시세 방향이 아니다. 부호(+)가 방향을 말하고 색은 잉크다.
  • 선택 상태(결제 수단·필터 탭)를 면 하나로 알리지 않는다. bg-transparent-selected 는 APCA 바닥 아래(Lc 0)라 물리적으로 안 보인다. stroke-neutral-contrast 테두리와 글자 굵기가 함께 움직인다 (finch-seed §4).

모노톤에서 위험은 색이 아니라 잉크 채움 · 굵기 · 형태다. 이 알림은 bg-critical-weak 면 + fg-critical(잉크) bold + 삼각 아이콘이다. 등락 적색을 쓰면 "떨어졌다" 로 오독된다.

확인 버튼에 금액을 다시 적는다. 사용자가 마지막으로 보는 숫자와 실제로 나가는 숫자가 같은 줄에 있어야 한다.

Idempotency-Key(UUID v4)는 이 버튼을 처음 누를 때 한 번 만든다. 같은 클릭의 재시도는 같은 키다 (apiSpec 1.4). 캐릭터(핀치·블루치)를 넣지 않는다 — 충전 확인 단계는 AI 설명 자리가 아니다 (ia.md §4).

이 에러만 서버 왕복이 꼭 필요하다. 1회 한도와 0원 검증은 클라이언트가 미리 막지만(아트보드 7), 누적 한도는 GET /deposits/limit 을 받은 뒤 다른 탭·세션에서 충전이 일어나면 remainingAmount 가 낡는다. 그래서 이 문구가 도착하는 자리는 확인 화면이다.

잔여 금액은 detail.remainingAmount 에서 온다. 화면이 cumulativeLimit − depositedAmount 로 다시 계산하지 않는다 — 그 두 값도 같은 이유로 낡아 있다.

두 번째 버튼은 선택 사항이다. 넣으면 사용자가 금액 입력으로 돌아가지 않고 끝낼 수 있지만, 확인 화면의 금액과 실제 나가는 금액이 달라지는 유일한 자리이므로 라벨에 금액을 반드시 적는다. 라벨이 "충전하기" 뿐이면 5,000,000원이 나갈 것으로 읽힌다. 이 버튼은 새 멱등성 키를 쓴다 — 금액이 바뀌었으니 같은 키로 보내면 IDEMPOTENCY_CONFLICT 다 (apiSpec 1.4).

이 화면이 중복 충전을 만드는 자리다. 서버 문구는 "잠시 후 다시 시도해 주세요" 인데 화면에 재시도 버튼이 없으면 사용자는 원래 충전 버튼을 다시 누른다. 그건 새 멱등성 키가 되어 두 번째 충전이 된다.

그래서 셋을 함께 건다.
  • 재시도 버튼을 시트 안에 둔다. 같은 Idempotency-Key 로 재요청하므로 서버가 최초 결과를 그대로 돌려준다 (apiSpec 1.4).
  • 딤으로 원래 CTA 를 덮는다. bg-overlay + z-overlay. 덮지 않으면 뒤 버튼이 여전히 눌린다.
  • 뒤의 CTA 자체도 비활성으로 바꾼다. 딤은 시각적 차단이고 이건 입력 차단이다. 둘 중 하나만 하면 키보드·스크린리더로 뚫린다.
문구를 새로 만들지 않았다 — GeneralErrorCode.IDEMPOTENCY_IN_PROGRESS 의 message 를 제목과 본문으로 쪼갠 것이다.

IDEMPOTENCY_CONFLICT(같은 키로 다른 요청)에는 화면을 그리지 않았다. 클라이언트 버그 신호이고 재시도 금지라서 사용자가 할 수 있는 일이 없다 — 일반 오류 화면으로 보낸다.

정렬은 최신순 고정이고 기간·종목 필터는 확장 범위다. 날짜 구분선은 occurredAt 으로 화면이 묶는다 — 응답에 그룹 필드는 없다.

필터 이름은 "충전" 이다. "입금" 으로 바꾸지 않는다. 이 탭은 모의 결제 건만 담고 초기 지급 1,000,000원은 없다. "입금" 이면 사용자가 초기 지급도 여기 있을 것으로 기대하는데 실제로는 없다 — 이름이 계약과 어긋나는 자리다 (명세 8장, apiSpec 8.2).

이 탭 금액의 합계 = GET /deposits/limit 의 depositedAmount 여야 한다 (여기서는 6,000,000원). 둘이 어긋나면 "충전 내역을 다 더했는데 한도 화면 숫자와 다르다" 가 된다. 초기 지급을 이 필터에 넣으면 바로 그렇게 된다.

불러오는 중
커서는 불투명 문자열이다. nextCursor 를 그대로 되돌려 보내고 파싱·해석하지 않는다 (apiSpec 1.5). 화면에 페이지 번호를 만들지 않는 이유도 그것이다 — 커서에서 번호를 꺼낼 수 없다.

첫 로드는 골격(아트보드 2), 추가 로드는 골격 행 + 스피너다. 이미 읽고 있는 목록이 통째로 골격으로 바뀌면 스크롤 위치를 잃는다.

nextCursor 가 null 이면 "마지막 내역입니다"(아트보드 10)로 바뀐다. 두 상태를 같은 자리에 그려 목록 끝에 무엇이 오는지가 늘 명시되게 한다 — 아무것도 없으면 사용자가 더 있는지 없는지 모른 채 계속 당긴다.
