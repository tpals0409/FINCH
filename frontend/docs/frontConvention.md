# 프론트엔드 내부 규약

이 문서는 `frontend/` 이하 코드에만 적용되는 규약을 정한다.
**다른 파트가 알아야 하는 크로스파트 계약은 [`docs/convention/frontConvention.md`](../../docs/convention/frontConvention.md)에 있다.**
확정·미확정 계약의 현재 상태는 [`contracts.md`](./contracts.md)에서 본다.

- 적용 범위: `frontend/` 이하 전체
- 작성일: 2026-08-19 / 최종 개정: 2026-08-20 (공통 API 규격 v0.3, AI 파트 회신 반영)
- 이 문서는 결론만 담는다. 검토 과정과 기각 이유의 상세는 작성자 개인 기록에 있다

브랜치 이름·커밋 메시지·이슈와 MR 절차는 [`gitConvention.md`](../../docs/convention/gitConvention.md)를 따르고
이 문서에서 다시 설명하지 않는다.

규약을 바꿔야 할 이유가 생기면 코드보다 이 문서를 먼저 고친다.
코드가 먼저 바뀌면 문서는 그 순간부터 거짓말이 된다.

## 1. 기술 스택과 선정 근거

기각한 대안을 함께 적는다. 나중에 "왜 이걸 안 썼나"를 다시 논의하지 않기 위해서다.

| 층                | 선택                        | 고른 이유                                                                                                               | 기각한 것과 이유                                                                                                                                           |
| ----------------- | --------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 번들러·프레임워크 | Vite + React SPA            | 로그인 이후 개인화 화면만 있어 SEO가 필요 없다. 차트와 실시간 시세가 전부 클라이언트 몫이다                             | **Next.js** — RSC와 hydration 경계를 다루는 비용이 얻는 것보다 크다. 서버 렌더링으로 얻을 이득이 이 서비스에는 없다                                        |
| 언어              | TypeScript                  | API 명세가 이미 유니온 타입으로 촘촘하다. 명세를 타입으로 그대로 옮기면 된다                                            | **JavaScript** — 명세의 유니온을 런타임 분기로 다시 쓰게 된다                                                                                              |
| 서버 상태         | TanStack Query              | 명세가 캐시 TTL과 429 `Retry-After`를 못 박아 두었고, 이것이 `staleTime`·`retry`·`retryDelay`에 그대로 대응된다         | **직접 구현한 fetch 훅** — 캐시·중복 요청 제거·재시도를 손으로 다시 만들게 된다. **SWR** — 재시도 정책 제어가 얕다                                         |
| 클라이언트 상태   | Zustand                     | 서버 상태를 TanStack Query가 가져가면 남는 것이 주문 입력 폼과 탭 선택 정도다                                           | **Redux Toolkit** — 이 규모에 과하다. 보일러플레이트가 상태의 양을 넘어선다. **Context만 사용** — 값이 바뀔 때 구독자 전체가 리렌더된다                    |
| 차트              | lightweight-charts          | 캔들·거래량 전용이고 45KB 수준이다                                                                                      | **Recharts** — 캔들과 크로스헤어가 약하다. 두 라이브러리를 함께 쓰면 번들이 두 배가 되므로, 진단 지표(HHI·비중) 같은 단순 그래프는 SVG 막대를 직접 그린다  |
| 스타일            | Tailwind + Radix Primitives | 명세에 다크모드 팔레트가 이미 있다. 토스형 UI는 바텀시트·탭 위주라 Radix는 그 부분만 골라 쓴다                          | **shadcn/ui 전면 도입** — 데스크톱 폼 위주 구성이라 모바일에서 절반은 쓰지 않는다. **CSS-in-JS(emotion 등)** — 런타임 비용이 있고 Tailwind와 역할이 겹친다 |
| 런타임 검증       | Zod                         | 주문 폼 검증과 API 응답 스키마 검증 양쪽에 쓴다. 스키마 하나에서 타입을 뽑아 쓸 수 있다                                 | **타입 단언만 사용** — 백엔드·AI 응답이 명세와 어긋나도 화면이 깨진 뒤에야 안다                                                                            |
| 목 서버           | MSW                         | 서비스 워커 층에서 가로채므로 애플리케이션 코드에 목 분기가 남지 않는다. AI 파트 인도 시점과 무관하게 프론트가 진행된다 | **JSON 파일 import** — 실제 연동으로 전환할 때 호출부를 전부 고치게 된다                                                                                   |

버전은 이 문서에 적지 않는다. `package.json`이 단일 진실 원천이다.

### 스택을 되돌릴 조건

- 상태 관리: Zustand 스토어가 5개를 넘고 스토어 간 참조가 생기면 구조를 다시 본다
- 차트: 직접 그린 SVG 그래프가 3종을 넘으면 경량 차트 라이브러리 추가를 재검토한다

## 2. 폴더 구조

```
frontend/
├── public/
├── docs/                    # 프론트 설계 문서 (아키텍처, 타입 정의, 컴포넌트 규약)
└── src/
    ├── app/                 # 앱 진입점, 라우터, 전역 프로바이더, 에러 경계
    ├── pages/               # 라우트 단위 화면. 데이터 조합과 레이아웃만 담당
    ├── features/            # 도메인 기능 단위. 이 프로젝트의 실제 무게중심
    │   └── {feature}/
    │       ├── api/         # 이 기능의 쿼리·뮤테이션 훅
    │       ├── components/  # 이 기능 안에서만 쓰는 컴포넌트
    │       ├── hooks/       # 이 기능 안에서만 쓰는 훅
    │       ├── model/       # 이 기능의 타입, Zod 스키마, 스토어
    │       └── lib/         # 이 기능의 순수 함수
    ├── shared/
    │   ├── ui/              # 도메인을 모르는 컴포넌트 (Button, BottomSheet, Skeleton)
    │   ├── api/             # HTTP 클라이언트, 인터셉터, 쿼리 클라이언트 설정
    │   ├── lib/             # 포매터, 날짜, 숫자 등 순수 유틸
    │   ├── hooks/           # 도메인 무관 훅 (useDebounce, useMediaQuery)
    │   ├── config/          # 환경변수 접근, 상수, 쿼리 키 팩토리
    │   └── types/           # 여러 기능이 공유하는 타입
    ├── styles/              # Tailwind 진입 CSS, 디자인 토큰
    └── mocks/               # MSW 핸들러와 픽스처
```

### 각 디렉토리의 책임

| 경로        | 책임                                                                    | 여기에 두면 안 되는 것                                                 |
| ----------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `app/`      | 라우터 정의, `QueryClientProvider` 등 전역 프로바이더, 최상위 에러 경계 | 화면 구현, 비즈니스 로직                                               |
| `pages/`    | 라우트에 대응하는 화면 조립. URL 파라미터를 읽어 `features`에 넘긴다    | 재사용 컴포넌트 정의, API 호출 상세                                    |
| `features/` | 하나의 도메인 관심사에 필요한 모든 것                                   | 다른 feature에서 쓰려고 만든 코드                                      |
| `shared/`   | 두 개 이상의 feature가 쓰는 것                                          | 도메인 지식. `shared/ui`의 컴포넌트는 "주문"이나 "종목"을 알면 안 된다 |
| `mocks/`    | MSW 핸들러                                                              | 프로덕션 번들에 들어가는 코드                                          |

### 의존 방향

```
app → pages → features → shared
```

**한 방향으로만 흐른다.** `shared`는 `features`를 import하지 않는다.
`features/order`가 `features/stock`을 직접 import하지 않는다.
두 feature가 같은 것을 필요로 하면 `shared`로 올린다.

feature 간 참조가 정말 필요하면 `pages`에서 조립해 props로 내린다.
feature끼리 서로를 부르기 시작하면 폴더가 나뉘어 있어도 결합은 하나가 된다.

ESLint의 `import-x/no-restricted-paths`가 이 방향을 강제한다.
규칙에 걸리면 우회하지 말고 구조를 다시 본다.

### feature를 언제 나누나

라우트 단위가 아니라 **도메인 단위**로 나눈다.
같은 화면에 있어도 관심사가 다르면 다른 feature다.
반대로 화면이 셋이어도 같은 도메인이면 하나의 feature다.

## 3. 네이밍 규칙

| 대상            | 규칙                                               | 예                                        |
| --------------- | -------------------------------------------------- | ----------------------------------------- |
| 컴포넌트 파일   | PascalCase, `.tsx`                                 | `OrderSheet.tsx`                          |
| 컴포넌트 이름   | PascalCase. 파일명과 동일                          | `export function OrderSheet()`            |
| 훅 파일·이름    | camelCase, `use` 접두                              | `useOrderForm.ts` / `useOrderForm()`      |
| 유틸 파일       | camelCase                                          | `formatCurrency.ts`                       |
| 유틸 함수       | 동사로 시작                                        | `formatPrice()`, `createIdempotencyKey()` |
| 타입·인터페이스 | PascalCase. 접두사 `I`·접미사 `Type`을 쓰지 않는다 | `Order`, `StockQuote`                     |
| Zod 스키마      | PascalCase + `Schema`                              | `OrderSchema`                             |
| 상수            | SCREAMING_SNAKE_CASE                               | `MAX_QUANTITY`                            |
| 상수 파일       | camelCase                                          | `queryKeys.ts`                            |
| 디렉토리        | camelCase                                          | `features/orderHistory/`                  |
| CSS 클래스      | Tailwind 유틸리티만. 커스텀 클래스는 만들지 않는다 | —                                         |

### 세부 규칙

**불리언은 `is` / `has` / `can` / `should` 로 시작한다.** `loading`이 아니라 `isLoading`이다.

**이벤트 핸들러는 `handle`, 그 props는 `on`으로 쓴다.**

```tsx
<OrderButton onSubmit={handleSubmit} />
```

**타입은 스키마에서 뽑아 쓴다.** 같은 모양을 두 번 적지 않는다.

```ts
export const OrderSchema = z.object({ ... });
export type Order = z.infer<typeof OrderSchema>;
```

**서버 응답 타입과 화면 타입을 구분한다.** 응답 타입은 `~Response`, 화면에서 쓰는 형태는 접미사 없이 쓴다.
변환은 API 레이어에서 한 번만 한다.

백엔드는 `camelCase`, AI 서비스는 `snake_case`로 필드를 준다.
**AI 응답 타입에는 `Ai` 접두를 붙여 어느 계열의 응답인지 이름에서 드러낸다** (`AiDiagnosisResponse`).
정규화를 거친 화면 타입에는 접두를 붙이지 않는다.

**축약하지 않는다.** `btn`, `usr`, `cfg`를 쓰지 않는다.
관례가 굳은 것(`id`, `url`, `api`)만 예외다.

**barrel 파일(`index.ts`)은 feature 경계에만 둔다.**
모든 폴더에 두면 순환 참조가 생기고 트리셰이킹이 막힌다.

## 4. 상태 경계

상태를 어디에 둘지가 이 프로젝트에서 가장 자주 틀리는 지점이다.
**먼저 종류를 판정하고, 그다음에 도구를 고른다.** 순서가 반대면 전부 전역 상태가 된다.

| 종류                 | 판정 기준                                   | 도구                              |
| -------------------- | ------------------------------------------- | --------------------------------- |
| 서버 상태            | 서버가 원본을 가진다. 내가 아니어도 바뀐다  | TanStack Query                    |
| URL 상태             | 새로고침·공유·뒤로가기에서 살아 있어야 한다 | React Router의 경로·쿼리 파라미터 |
| 클라이언트 전역 상태 | 서버가 모르고, 여러 화면이 공유한다         | Zustand                           |
| 로컬 상태            | 한 컴포넌트 안에서만 쓴다                   | `useState` / `useReducer`         |

### 서버 상태 — TanStack Query

시세, 종목 정보, 포트폴리오, 주문 내역, AI 응답은 전부 서버 상태다.
**서버 상태를 Zustand에 복사하지 않는다.** 복사하는 순간 무효화 시점이 두 곳이 되고, 둘은 반드시 어긋난다.

- 쿼리 키는 `shared/config/queryKeys.ts`의 팩토리에서만 만든다. 문자열 배열을 호출부에 직접 쓰지 않는다
- `staleTime`은 데이터 성격에 맞춘다. 실시간 시세는 0에 가깝게, 종목 마스터처럼 잘 안 바뀌는 것은 길게 잡는다
- 명세가 캐시 TTL을 못 박은 엔드포인트는 그 값을 `staleTime`에 그대로 반영한다
- 뮤테이션 성공 후 무효화 대상은 해당 뮤테이션 훅 안에 적는다. 호출하는 컴포넌트가 알 필요 없다

### URL 상태

**공유했을 때 같은 화면이 나와야 하는 것은 전부 URL에 둔다.**

- 종목 코드, 탭 선택, 차트 기간, 목록 필터
- 판정: 뒤로가기를 눌렀을 때 되돌아가야 하면 URL 상태다
- 커서 페이징의 커서는 URL에 넣지 않는다. 불투명 문자열이고 목록은 최신순이라 공유해도 같은 화면이 나오지 않는다

### 클라이언트 전역 상태 — Zustand

여기 들어갈 것은 많지 않다. 늘어나면 대개 서버 상태를 잘못 옮긴 것이다.

- 인증 세션, 테마, 진행 중인 주문 입력값, 전역 토스트·바텀시트 제어
- 스토어는 도메인 단위로 나누고 `features/{feature}/model/`에 둔다. 전역 스토어 하나에 몰지 않는다
- 셀렉터로 필요한 값만 구독한다. 스토어 전체를 구독하면 관련 없는 변경에도 리렌더된다

**Access Token은 Zustand 스토어(메모리)에만 둔다.** `localStorage`·`sessionStorage`에 쓰지 않는다.
Refresh Token은 `HttpOnly` 쿠키라 JS에서 보이지 않으므로 프론트가 보관할 것이 없다.
새로고침으로 Access Token이 사라지는 것은 정상 동작이고, 앱 부팅 시 `POST /auth/refresh`로 복구한다.

### 로컬 상태

나머지 전부다. **의심스러우면 `useState`로 시작한다.**
끌어올리는 것은 쉽지만 내리는 것은 어렵다.

주문 수량 입력, 충전 금액 입력, 바텀시트 열림 여부가 여기 속한다.

## 5. API 레이어 규약

### 계층

```
컴포넌트 → 쿼리 훅(features/{feature}/api) → API 함수(features/{feature}/api) → HTTP 클라이언트(shared/api)
```

**컴포넌트는 `fetch`를 직접 부르지 않는다.** 예외 없다.

### HTTP 클라이언트

백엔드(`/api/v1`)와 AI 서비스(`/api/ai/v1`)는 봉투·필드 네이밍·에러 형식이 모두 다르다.
따라서 `shared/api`에 **서비스별 클라이언트를 두되 공통 코어 하나를 공유한다.**
코어가 하는 일은 요청 조립, 토큰 주입, `X-Request-Id` 수집, 재시도 정책이고,
서비스별 클라이언트가 하는 일은 봉투 해체와 에러 정규화다.

- 응답은 Zod 스키마로 검증한 뒤 반환한다. 검증 실패는 네트워크 에러와 구분되는 별도 에러 타입으로 던진다
- HTTP 에러 응답은 클라이언트 층에서 정규화된 에러 객체로 변환한다. 상태 코드가 이 층 밖으로 새어 나가지 않는다
- 프론트가 AI 서버를 직접 부를지 백엔드를 경유할지는 아직 미확정이다([`contracts.md`](./contracts.md) §2 참고). 이 계층 구조는 어느 쪽으로 정해져도 살아남는다 — 경유로 정해지면 AI 클라이언트의 baseURL과 에러 어댑터만 백엔드 계열로 바뀐다

### 정규화 어댑터

**응답 형태와 단위 변환은 API 레이어에서 한 번만 한다.**

- 백엔드 성공 응답은 봉투가 없고, AI 성공 응답은 공통 봉투에 담겨 온다. 어댑터가 봉투를 벗겨 리소스만 위로 올린다
- 에러는 백엔드 `{isSuccess, code, message, result}`, AI `{error:{code,message,detail}, request_id}`로 형태가 다르다. 어댑터가 둘을 `{code, message, detail, requestId}` 하나로 정규화한다
- `snake_case` → `camelCase` 변환도 여기서 끝낸다
- **화면 컴포넌트는 값이 어느 서버에서 왔는지 몰라야 한다.** 컴포넌트에서 `isSuccess`나 `request_id`가 보이면 어댑터가 빠진 것이다
- 어댑터는 `shared/api`에만 두고 feature마다 만들지 않는다. 서버가 둘이면 어댑터도 둘이다

### 에러 처리 위치

**층마다 책임이 다르다. 한 층에서 다 처리하려 하면 나머지 층이 전부 에러를 다시 확인하게 된다.**

| 층              | 책임                                                                         |
| --------------- | ---------------------------------------------------------------------------- |
| HTTP 클라이언트 | 에러 정규화, 인증 만료 시 갱신·로그아웃, 재시도 정책 적용                    |
| 쿼리 훅         | 이 요청 고유의 재시도 여부와 `staleTime` 결정. 여기서 토스트를 띄우지 않는다 |
| 컴포넌트        | 화면에 보일 상태(로딩·빈 상태·에러 UI) 결정                                  |
| 에러 경계       | 컴포넌트가 처리하지 못한 렌더 에러 수습                                      |

**분기는 정규화된 `code` 문자열로만 한다.** `message` 문장이나 HTTP 상태 코드로 분기하지 않는다.
`message`는 서버가 완성해서 주는 사용자 노출용 문장이므로 화면에 그대로 쓰고 하드코딩하지 않는다.

**개별 `try/catch`로 에러를 삼키지 않는다.** 삼키면 그 요청은 영원히 로딩 상태로 남는다.

### 인증 인터셉터

**세션 처리는 HTTP 상태 숫자로 판단하지 않는다. 정규화된 `code` 문자열로만 판단한다.**
세션에 손대는 코드는 아래 셋뿐이다. **그 밖의 모든 코드는 세션을 건드리지 않고 호출한 쪽에 그대로 넘긴다.**
`code`가 없는 응답(프록시가 내는 HTML 401 등)도 매칭이 실패하므로 같은 경로로 안전하게 지나간다.

- `AUTH_TOKEN_EXPIRED` → `POST /auth/refresh` 호출, 성공 시 원요청을 1회 재시도한다. 실패하면 세션을 비우고 로그인 화면으로 보낸다
- `AUTH_INVALID_TOKEN` → 재시도 없이 로그인 화면으로 보낸다
- `AUTH_REFRESH_TOKEN_MISSING` → 조용히 비로그인 상태로 둔다. 로그인 화면으로 강제 이동하지 않는다.
  쿠키 자체가 없는 최초 방문자와 세션 만료를 같은 코드로 주면 최초 방문자까지 로그인 화면으로 튕기므로
  백엔드가 둘을 코드로 나눠 뒀다([`contracts.md`](./contracts.md) C24)

**숫자로 분기하면 안 되는 이유.** [`contracts.md`](./contracts.md) C11의 통과 규칙 때문에 401을 내는 주체가
우리 서비스 하나가 아니다. 백엔드와 AI 서버 사이의 내부 인증이 어긋나면 AI 서버도 `UNAUTHORIZED`(401)를
내고, 그 상태 코드가 그대로 프론트까지 내려온다. 이 401은 사용자 세션과 무관하다. 숫자로 분기하면
이것을 세션 만료로 오인해 AI 분석 탭을 눌렀을 뿐인 사용자를 로그아웃시킨다. 화이트리스트는 모르는
코드가 와도 세션을 건드리지 않으므로 이 사고가 나지 않는다.

이 방식은 **`AUTH_` 접두 코드가 우리 서비스 사용자 인증 전용**이라는 전제 위에 있다. 지금은 성립하지만
(AI 코드 목록에 `AUTH_` 접두가 없다) 이 전제가 계속 성립하도록 GitLab 이슈 #18로 백엔드·AI 양쪽에
이름공간 합의를 요청해 뒀다.

- **갱신 요청은 동시에 하나만 나가게 한다.** 동시에 만료된 요청 여러 개가 각자 갱신을 부르면 Refresh 회전과 겹쳐 서로를 무효화한다. 진행 중인 갱신 Promise를 공유하고 대기시킨다
- 재시도는 한 번만 한다. 갱신 직후 재시도한 요청이 다시 `AUTH_INVALID_TOKEN`이면 재로그인이다
- 갱신 요청 자체는 재시도 대상에서 제외한다

### 재시도와 429 `Retry-After`

명세가 429에 `Retry-After` 헤더를 규정했다. 이 값을 무시하고 지수 백오프만 쓰면 차단 시간이 길어진다.

- **429는 `Retry-After` 값을 파싱해 그 시간만큼 기다린 뒤 재시도한다.** 헤더가 없으면 지수 백오프로 대체한다
- 4xx(429 제외)는 재시도하지 않는다. 같은 요청을 다시 보내도 결과가 같다
- 5xx와 네트워크 오류는 지수 백오프로 최대 2회까지 재시도한다
- 뮤테이션은 기본적으로 재시도하지 않는다. **주문 요청을 자동 재시도하면 중복 주문이 된다**

### 멱등성 키

`POST /charges`와 `POST /orders`는 `Idempotency-Key` 헤더가 필수다.

- 키는 클라이언트가 UUID v4로 만든다. 생성 유틸은 `shared/lib`에 하나만 둔다
- **키의 수명은 사용자의 한 번의 클릭이다.** 같은 클릭에서 파생된 재시도는 같은 키를 쓰고, 새 클릭은 새 키를 만든다. 폼 마운트 시점에 만들어 재사용하면 다른 주문이 같은 키를 쓰게 된다
- `IDEMPOTENCY_IN_PROGRESS`는 짧게 기다린 뒤 **같은 키로** 재시도한다. 새 키로 바꾸면 이중 주문이 된다
- `IDEMPOTENCY_CONFLICT`는 프론트 버그 신호다. 재시도하지 않고 오류로 노출한다

### 커서 페이징

- **커서는 불투명 문자열이다.** 파싱·조작·해석하지 않고 `nextCursor`를 그대로 다음 요청에 넣는다
- `size`는 기본 30, 최대 100. 화면에서 임의로 늘리지 않는다
- 목록은 `useInfiniteQuery`로 다루고 `hasNext`로 종료를 판정한다. `items.length`로 판정하지 않는다

### AI 응답 처리 방침

**AI 6종은 전부 일반 요청/응답이다.** `ai/docs/openapi.json`의 6개 엔드포인트가 모두 단일 JSON 봉투를 반환한다.
AI 호출도 다른 쿼리·뮤테이션과 똑같이 다룬다. 별도 전송 계층을 만들지 않는다.

> **SSE 파싱 방침은 폐기됐다 (커밋 `34ed34a`, 2026-08-20).**
> 이 자리에는 "`EventSource`가 GET 전용이라 `fetch` + `ReadableStream` + `TextDecoder`로 직접 파싱한다"는
> 규약이 있었다. 설계에서 스트리밍이 빠졌으므로 함께 지웠다.
> **`shared/api`에 스트림 파서를 만들지 않는다.** 다시 필요해지면 AI 파트의 구현을 먼저 확인하고 이 절을 되살린다.

- AI 경로 문자열은 `shared/config` 상수 한 곳에 모은다. 백엔드 중계 경로가 확정되면 그 파일만 고친다
- 응답의 `data_as_of`·`disclaimer`는 **Zod 스키마에서 optional로 둔다.** 백엔드 중계 후에도 남아 있을지 확인되지 않았다. 없으면 그 표기만 생략하고 화면은 정상 동작해야 한다
- AI 요청은 느리다. `staleTime`을 길게 잡고 화면 진입마다 다시 부르지 않는다
- **프론트는 AI 응답을 조립하지 않는다.** 수치 치환·검증은 AI 서버가 끝낸 상태로 온다

### 시세 구독 계층

시세는 서버가 웹소켓 슬롯과 REST 폴링 폴백의 두 경로로 내려보내고, **두 경로의 메시지 스키마는 같다.**
프론트는 폴링 전제로 먼저 구현하는 것을 승인받았다. 폴링은 임시 코드가 아니라 최종 구조의 폴백 경로다.

- 화면 컴포넌트는 폴링도 웹소켓도 직접 부르지 않는다. `subscribe(ticker, callback)` / `unsubscribe(ticker)` **추상화 계층 뒤에 구현을 숨긴다.** 웹소켓 전환 시 이 계층의 내부만 교체한다
- **화면에 보이는 종목만 구독한다.** 관심 종목 전체 상시 구독은 하지 않는다. 목록 화면에서는 뷰포트에 보이는 종목만 구독하고 스크롤 아웃 시 해제한다
- 슬롯 배분과 회수는 서버 책임이다(참조 카운팅 + LRU). 프론트가 우선순위를 올려보내지 않는다
- **프론트의 책임은 구독·해제 신호를 정확히 보내는 것뿐이다.** 해제 누락은 유령 시청자를 만들어 슬롯을 낭비시킨다. 컴포넌트 unmount와 페이지 이탈(`beforeunload`·`visibilitychange`)에서 해제를 보장한다
- 다건 조회 `GET /stocks/prices`는 최대 50건이다. 캐시 미스 항목은 `price: null, stale: true`로 오므로 그 항목만 "시세 지연"으로 표시하고 전체를 에러로 만들지 않는다
- 동시 구독 한도 수치는 확정값이 아니다 (미확정 — 기능명세 S0-1 실측 대기). 한도를 상수로 코드에 박지 않는다
- 갱신 주기와 시세 실패 허용 시간도 미확정이다 (미확정 — 기능명세 S0-2·S0-3, 8/26 결정 회의)

## 6. 컴포넌트 규약

### 기본

- **함수 컴포넌트와 화살표 함수 중 `function` 선언을 쓴다.** 호이스팅되고 스택 트레이스에 이름이 남는다
- `React.FC`를 쓰지 않는다. props 타입을 직접 적는다
- **한 파일에 한 컴포넌트.** 그 파일 안에서만 쓰는 작은 하위 컴포넌트는 예외로 같은 파일에 둔다
- props 타입은 `{ComponentName}Props`로 이름 짓고 export하지 않는다. 밖에서 필요해지면 그때 export한다
- **props는 7개를 넘지 않게 한다.** 넘으면 컴포넌트가 두 가지 일을 하고 있다는 신호다

### 컴포넌트 분류

| 종류            | 위치                            | 규칙                                                                    |
| --------------- | ------------------------------- | ----------------------------------------------------------------------- |
| UI 컴포넌트     | `shared/ui`                     | 도메인을 모른다. 서버 데이터를 직접 가져오지 않는다. props로만 동작한다 |
| 도메인 컴포넌트 | `features/{feature}/components` | 해당 도메인 타입을 알아도 된다. 쿼리 훅을 직접 쓸 수 있다               |
| 페이지          | `pages`                         | 라우트 파라미터를 읽고 도메인 컴포넌트를 배치한다                       |

**데이터 페칭은 그 데이터를 실제로 쓰는 컴포넌트에서 한다.**
위에서 받아 여러 단계로 내리지 않는다. props가 세 단계를 넘어 흐르면 페칭 위치가 잘못된 것이다.

### 포매팅과 표기

**변환 함수는 `shared/lib`에 모으고 컴포넌트에서 인라인으로 계산하지 않는다.**
`toFixed`나 `toLocaleString`이 컴포넌트 JSX 안에 보이면 규약 위반이다.
같은 숫자가 화면마다 다르게 보이는 사고가 여기서 나온다.

색은 값이 아니라 **의미 토큰**으로 참조한다. `text-red-500`이 아니라 등락 방향을 나타내는 토큰을 쓴다.
관례가 바뀌거나 색맹 대응이 필요해지면 토큰 한 곳만 고친다.

표기 규약의 내용 자체는 크로스파트 계약이다. [`docs/convention/frontConvention.md`](../../docs/convention/frontConvention.md) §1을 본다.

### 로딩과 빈 상태

**데이터를 표시하는 컴포넌트는 세 가지 상태를 모두 정의한다: 로딩, 빈 상태, 에러.**
셋 중 하나라도 없으면 미완성으로 본다.

- 로딩은 스피너 대신 실제 레이아웃과 같은 크기의 스켈레톤을 쓴다. 레이아웃이 흔들리지 않는다
- 빈 상태는 에러가 아니다. 다르게 표시한다
- 주문 화면에는 네 번째 상태가 있다. **정규장(09:00~15:30 KST) 밖에서는 주문 버튼을 비활성화하고 이유를 문구로 보여준다.** 비활성 상태를 로딩으로 표시하면 사용자가 기다린다

### 성능

- `memo`·`useMemo`·`useCallback`을 습관적으로 붙이지 않는다. **측정한 뒤에 붙인다**
- 예외: 차트처럼 비용이 확실히 큰 컴포넌트, `useEffect` 의존성으로 들어가는 객체·함수
- 리스트의 `key`에 배열 인덱스를 쓰지 않는다. 서버가 준 식별자를 쓴다

## 7. 에러 경계 단위

**에러 경계를 하나만 두면 어디서 터져도 화면 전체가 사라진다.**
차트 하나가 죽었다고 주문 버튼까지 사라져서는 안 된다.

| 단위    | 위치                          | 대체 화면                      |
| ------- | ----------------------------- | ------------------------------ |
| 앱 전역 | `app/`                        | 전체 오류 화면 + 새로고침      |
| 라우트  | 각 라우트 진입부              | 해당 화면 오류 + 이전 화면으로 |
| 위젯    | 독립적으로 실패해도 되는 블록 | 그 블록만 오류 표시 + 재시도   |

**위젯 단위 경계를 반드시 두는 곳:**

- 차트 — 라이브러리 초기화 실패가 화면 전체를 죽이지 않게 한다
- AI 응답 블록 — 타임아웃과 스키마 불일치가 잦은 지점이다. AI 서비스가 죽어도 시세·주문은 살아 있어야 한다
- 실시간 시세 영역 — WebSocket 끊김이 정적 정보까지 지우지 않게 한다

### 규칙

- 에러 경계는 렌더 에러만 잡는다. **이벤트 핸들러와 비동기 콜백의 에러는 잡지 못한다.** 그쪽은 직접 처리한다
- TanStack Query 에러를 경계로 올리려면 `throwOnError`를 명시한다. 기본값에 기대지 않는다
- 모든 대체 화면에는 재시도 수단을 둔다. 재시도할 수 없으면 무엇이 안 되는지라도 적는다
- **에러 메시지는 서버가 준 `message`를 쓰고, 스택이나 응답 원문은 노출하지 않는다.** 원문은 콘솔에 남긴다
- 오류를 리포트할 때는 응답 헤더의 `X-Request-Id`(AI는 본문 `request_id`)를 함께 담는다. 서버 로그와 잇는 유일한 키다

## 8. 반응형 기준

**모바일 우선이다.** 기본 스타일이 모바일이고, 넓은 화면은 `min-width` 미디어 쿼리로 덧붙인다.
Tailwind의 기본 방향과 같다. `max-width` 쿼리를 섞어 쓰지 않는다.

### 브레이크포인트

Tailwind 기본값을 쓴다. 커스텀 브레이크포인트를 추가하지 않는다.

| 이름   | 최소 너비 | 대상                          |
| ------ | --------- | ----------------------------- |
| (기본) | 0         | 모바일 세로. **주 개발 대상** |
| `sm`   | 640px     | 큰 모바일, 세로 태블릿        |
| `md`   | 768px     | 태블릿                        |
| `lg`   | 1024px    | 데스크톱                      |

### 규칙

- **기준 뷰포트는 375px다.** 여기서 깨지면 완성이 아니다
- 최소 지원 너비 320px. 가로 스크롤이 생기면 버그로 본다
- 데스크톱은 중앙 정렬 + 최대 너비 제한으로 대응한다. **데스크톱 전용 레이아웃을 따로 만들지 않는다.** 만드는 순간 화면 수가 두 배가 된다
- 터치 대상은 최소 44×44px를 확보한다
- 고정 픽셀 폭을 쓰지 않는다. `%`, `flex`, `grid`로 푼다
- 하단 고정 요소(주문 버튼, 탭 바)는 `env(safe-area-inset-bottom)`을 반영한다. 노치 기기에서 잘린다
- 가로 스크롤이 필요한 영역은 그 컨테이너 안에서만 스크롤한다. `body`가 가로로 밀리면 안 된다

### 확인 순서

375px에서 만들고, 320px에서 깨지지 않는지 보고, 그다음 넓은 화면을 본다.
넓은 화면부터 만들면 좁은 화면에서 줄일 곳이 없다.

## 9. 로컬 개발 환경

프론트(5173)와 백엔드(8080)의 포트 차이로 인한 쿠키·CORS 설정을 각자 맞추지 않는다.
**Vite dev server의 proxy로 `/api` 요청을 백엔드에 넘겨 브라우저 입장에서 같은 오리진으로 만든다.**

이러면 `credentials: 'include'`, CORS allow-credentials, 쿠키 도메인 설정이 로컬에서 전부 불필요해지고,
운영(Nginx가 같은 도메인에서 정적 파일과 API를 함께 서빙)과 환경 차이도 사라진다.

```ts
// vite.config.ts
server: { proxy: { '/api': 'http://localhost:8080' } }
```

- 프록시 대상 주소는 `.env`로 빼고 `.env.example`에 키를 남긴다. 코드에 호스트를 박지 않는다
- AI 서비스의 로컬 포트와 운영 라우팅 경로는 아직 미확정이다 (미확정 — AI 파트 회신 대기). 확정되면 프록시 규칙을 한 줄 더 추가한다
- MSW를 쓰는 동안은 프록시가 필요 없다. 실제 백엔드로 붙일 때 MSW를 끄고 프록시를 켠다. 둘을 동시에 켜면 어느 쪽이 응답했는지 알 수 없다
