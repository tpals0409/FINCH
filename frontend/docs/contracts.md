# 계약 현황

프론트가 의존하는 크로스파트 계약이 **어디까지 확정됐고 무엇을 기다리는지** 한곳에 모은 문서다.

이 문서의 목적은 다음 작업자와 에이전트가 원본 문서 다섯 개를 다시 읽지 않고도
무엇이 정해졌는지 알게 하는 것이다. **규약의 본문은 여기가 아니라 원본에 있다.**
값이 어긋나면 원본이 진실이다.

- 기준일: 2026-08-20
- 참조 원본
  - 공통 API 규격 v0.3 — 백엔드 파트 산출물(태스크 0-5). `apiSpec v0.1`보다 **우선한다**
  - [`docs/api/apiSpec.md`](../../docs/api/apiSpec.md) — 백엔드 API 명세 v0.1 (초안)
  - [`docs/spec/featureSpec.md`](../../docs/spec/featureSpec.md) — 기능 명세서 v2.1
  - [`ai/docs/api-spec.md`](../../ai/docs/api-spec.md) — AI 파트 인터페이스 계약
  - AI 파트 회신 (2026-08-20, 4문항)
- 관련 규약: [`docs/convention/frontConvention.md`](../../docs/convention/frontConvention.md) (크로스파트) ·
  [`frontConvention.md`](./frontConvention.md) (프론트 내부)

### 2.1 P1 — AI 호출 경로 두 방식의 프론트 영향 비교

**결정 전에 프론트가 이 표를 근거로 의견을 낼 수 있어야 한다.**
아래는 프론트 관점의 영향만 적은 것이고, 인증 로직 중복 비용은 백엔드·AI 파트가 판단할 몫이다.

| 관점                 | A. 프론트 → AI 서버 직접 호출                                                                                                                       | B. 프론트 → 백엔드 → AI 서버 경유                                                                                                                                                                                              |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| HTTP 클라이언트 개수 | **2개.** `/api/v1`(camelCase, 봉투 없음)과 `/api/ai/v1`(snake_case, 공통 봉투)을 각각 다룬다                                                        | **1개.** 백엔드가 AI 응답을 자기 형식으로 재포장하면 프론트는 한 계열만 안다. 재포장 없이 그대로 중계하면 A와 같아진다                                                                                                         |
| 정규화 어댑터        | **2벌.** 봉투 해체·네이밍 변환·에러 형식 어댑터가 계열별로 필요                                                                                     | 1벌. 다만 **백엔드가 AI 에러 코드를 자기 코드 체계로 매핑해 줘야** 진짜 1벌이 된다                                                                                                                                             |
| 인증 검증 위치       | **AI 서버가 JWT를 직접 검증한다.** 검증 로직이 두 벌이 되고 서명 키 공유·만료 동기화 문제가 생긴다. 프론트는 같은 Access Token을 두 오리진에 보낸다 | **백엔드 한 곳.** AI 서버는 서비스 토큰만 신뢰한다. 프론트는 토큰을 한 곳에만 보낸다                                                                                                                                           |
| 401 갱신 흐름        | 두 서버가 각자 401을 던지므로 **갱신 인터셉터가 두 클라이언트에 걸린다.** 동시 만료 시 갱신 요청이 중복되지 않게 진행 중 Promise를 공유해야 한다    | 갱신 인터셉터 한 곳. 흐름이 단순하다                                                                                                                                                                                           |
| SSE 중계             | **불필요.** 프론트가 AI 서버의 스트림을 직접 읽는다. 지연이 가장 적다                                                                               | **필요.** 백엔드가 SSE를 중계해야 한다. Spring에서 스트림을 버퍼링 없이 통과시켜야 하고(`SseEmitter`/`ResponseBodyEmitter` + flush), 백엔드가 홉 하나만큼 지연과 실패 지점을 더한다. **중계 구현 비용은 백엔드 파트에 생긴다** |
| CORS · 오리진        | 오리진이 둘이므로 운영에서 AI 서버 CORS 설정이 필요하다. 로컬은 dev proxy 규칙을 두 개 둔다                                                         | 오리진이 하나. CORS 설정과 프록시 규칙이 한 벌                                                                                                                                                                                 |
| 장애 전파 경로       | **AI 장애가 AI 화면 블록에만 갇힌다.** 시세·주문은 백엔드만 보므로 영향이 없다. 위젯 단위 에러 경계로 충분하다                                      | **AI 장애가 백엔드 경유로 들어온다.** 백엔드가 AI 타임아웃을 자기 5xx로 올리면 프론트가 AI 장애와 백엔드 장애를 구분하지 못한다. **구분 가능한 에러 코드를 백엔드가 따로 내려줘야 한다**                                       |
| 프론트 작업량        | 클라이언트·어댑터가 두 벌이라 초기 비용이 크다. 다만 어차피 두 명세의 형태가 달라 어댑터는 필요하다                                                 | 초기 비용이 작다. 대신 백엔드 중계 스펙(에러 코드 매핑, SSE 통과)이 확정될 때까지 AI 연동을 시작할 수 없다                                                                                                                     |
| 되돌릴 비용          | A → B 전환: AI 클라이언트의 baseURL과 에러 어댑터만 백엔드 계열로 교체                                                                              | B → A 전환: 동일하게 클라이언트 한 벌 추가                                                                                                                                                                                     |

**프론트 입장의 잠정 결론**: A와 B의 프론트 비용 차이는 크지 않다.
어느 쪽이든 서비스별 클라이언트 + 정규화 어댑터 구조를 먼저 만들어 두면 전환 비용이 baseURL과
어댑터 교체로 끝난다. 결정을 기다리는 동안 프론트 작업이 멈추지 않는다.

**다만 SSE 중계 필요 여부는 프론트가 아니라 백엔드 비용이므로, 결정은 백엔드·AI 협의로 맡긴다.**
프론트가 요청할 것은 하나다 — **B로 정할 경우 AI 장애와 백엔드 장애를 구분할 수 있는 에러 코드를
따로 내려 달라.** 구분이 없으면 AI 블록만 죽이는 에러 경계를 만들 수 없다.

### 작업 중 새로 발견한 것

X3 · X4 · X5는 이번 작업에서 처음 정리한 항목이다.
공통적인 원인은 **`apiSpec v0.1`이 v0.3 확정 내용을 아직 반영하지 않은 것**이다.
개별 항목을 프론트 문서에서 계속 예외 처리하기보다 **apiSpec을 v0.3 기준으로 갱신하는 쪽이 맞고,
그것은 백엔드 파트 소유 문서이므로 프론트가 고치지 않고 보고만 한다.**

그 외 누락으로 관측한 것:

- **`GET /stocks/prices`의 `stale: true` 항목 스키마가 어느 문서에도 없다.** `price: null`일 때
  `changeRate`·`asOf` 등 나머지 필드가 어떻게 오는지(null인지 마지막 값인지) 정해지지 않았다.
  Zod 스키마를 정확히 못 짠다. 백엔드 확인 필요
- **구독·해제 신호의 전달 방식이 정해지지 않았다.** 공통 API 규격 v0.3 §7.3은 프론트가 신호를
  "보낸다"고만 하고 그 채널(웹소켓 메시지인지 REST 엔드포인트인지)을 정하지 않았다.
  폴링 선행 구현 단계에서는 추상화 계층 안에 갇히므로 당장 블로커는 아니다
- **로그아웃 엔드포인트가 명세에 없다.** Refresh 쿠키를 서버가 무효화해야 하는데
  `POST /auth/logout`류가 apiSpec v0.1과 공통 API 규격 v0.3 어디에도 없다. 백엔드 확인 필요
