# 프론트엔드 화면 목록·IA

이 문서는 프론트엔드가 만들 화면의 목록과 구조를 정한다.
역할 분담과 일정 산정의 기준이 되므로 **분담 가능한 단위**로 쪼개 적었다.

- 작성일: 2026-08-19 / 최종 개정: 2026-08-28 (기획서 기능 목록 대조 — AI 슬롯 내부 구성 구체화)
- UI 레퍼런스: 토스증권 / 플랫폼: 모바일 웹(반응형, 모바일 우선)
- 관련 문서: [`../../docs/convention/frontConvention.md`](../../docs/convention/frontConvention.md) ·
  [`contracts.md`](./contracts.md) · [`../../docs/api/apiSpec.md`](../../docs/api/apiSpec.md)

**이번 개정에서 뒤집힌 전제 네 가지.** 이전 판을 읽은 사람은 이것부터 본다.

1. **SSE는 폐기됐다.** AI 슬롯 6종이 전부 일반 요청/응답이다 (커밋 `34ed34a`).
2. **호출 경로는 프런트 → 백엔드 → AI다.** 프론트가 쓰는 Base URL은 `/api/v1` 하나이고 AI 서버를 직접 부르지 않는다.
3. **AI 기능은 6종이다.** 기능명세 §10.2의 3종은 낡았다.
4. **종목코드 파라미터는 `stockCode`로 통일한다.** AI 명세의 `ticker`를 프론트에서 쓰지 않는다.

경로가 확정되지 않은 항목은 `(잠정)`으로 남겼다.
**빈칸으로 두지 않고 무엇이 잠정인지 적는다.** 나중에 답이 왔을 때 채울 자리가 보여야 한다.

## 1. 화면 목록

`AI` 열은 AI 슬롯이 들어가는 화면을 표시한다. 슬롯 상세는 §4에 있다.
`티켓` 열은 그 화면을 구현하는 발행 스토리다.

- **자체 회원가입 폼은 없다.** 인증 수단은 카카오 OAuth 2.0 단일이고, 최초 로그인 시 서버가 계정·가상 계좌·1회차·초기 예수금 1,000,000원을 함께 만든다 (기능명세 §2.1, apiSpec §2.1). 이전 판의 `/signup` 화면은 삭제했다.
- 콜백 라우트는 카카오에 등록할 redirect URI와 같아야 한다. apiSpec §2.1의 예시가 `https://{도메인}/oauth/kakao`이므로 그 경로를 쓴다.
- 로그인 이후 화면은 전부 인증이 필요하다. 미인증 접근은 `/login`으로 보내고, 원래 가려던 경로를 `redirect` 쿼리 파라미터로 들고 가 로그인 후 되돌린다.

- 이전 판의 `거래 내역 /orders`를 **`매매 내역 /transactions`로 바꿨다.** 이 화면은 주문만이 아니라 원장 전체(초기 지급·충전·매수·매도·회차 개폐)를 보여주므로 이름과 경로를 백엔드 리소스에 맞춘다.

- 한도는 화면이 계산하지 않고 `GET /deposits/limit`의 `perRequestLimit`·`roundCumulativeLimit`·`remainingAmount`를 그대로 쓴다. **한도는 회차 단위이며 계좌 리셋으로 초기화된다.**

- **최근 검색어는 자기 라우트를 갖지 않는다.** 검색어가 비어 있을 때의 `/search` 초기 상태다. 라우트를 따로 두면 뒤로가기가 검색어 입력 사이에 끼어든다.
- **최근 본 종목은 등록 API가 없다.** `GET /stocks/{stockCode}` 호출 자체가 서버에 기록을 남긴다 (apiSpec §5.2). 프론트가 별도로 기록 요청을 보내지 않는다.
- **종목 상세는 거래정지 뱃지를 노출한다.** `suspended: true`면 뱃지 + `suspendedReason` 문구를 보여주고 매수·매도 진입을 막는다. 검색 결과 행에도 같은 뱃지를 쓴다 (기능명세 §4, §7.4).
- 주문은 **시장가 전용**이다. 지정가·미체결 관리·호가창은 범위 밖이다. 가격 입력 필드를 만들지 않는다.
- 주문 수량은 직접 입력 + **비율 버튼 10% / 25% / 50% / 최대**다. 비율의 분모는 화면이 계산하지 않고 `GET /orders/available`의 `maxQuantity`(매수)와 `holdingQuantity`(매도)를 쓴다.
- **정규장(09:00~15:30 KST) 외에는 주문 버튼을 비활성화**하고 사유 문구를 함께 보여준다. 비활성 판정도 화면의 시계가 아니라 `GET /orders/available`의 `tradable` / `reason`을 따른다. 화면이 자체 판정하면 서버와 어긋나 "눌리는데 거부되는" 상태가 생긴다.

#### AI가 이해한 나 — 위키 화면

AI 서버에 `/wiki/**` 4종이 구현돼 있고(AI 명세 §9) 그중 셋이 화면에서 호출된다.
`POST /wiki/theses`는 **화면에서 부르지 않는다** — 신규 매수를 감지한 AI 서비스가 대화 안에서 직접 묻고 스스로 기록한다(AI 명세 §9 수집 경로). 논지 입력 폼을 만들지 않는다.
기획서 §개인화 AI의 "종목별 투자 논리 기록 및 관리"가 이 화면과 종목 분석의 `thesis_check` 섹션 두 곳으로 나뉜다. 사용자가 대화에 응답하지 않으면 종목 상세 `tab=ai`에 유도 카드가 뜨는데(§4 3번 슬롯), **그것도 폼이 아니라 채팅으로 보내는 버튼이다.**

**호출 경로가 미확정이다.** `apiSpec.md` §10.1 표에 위키 3종이 없다. 표 마지막 줄이 "프론트 화면 범위가 확정되면 같은 규칙으로 추가한다"이고, 이 화면을 여기 등재하는 것이 그 선행 조건이다. 회신을 기다리는 동안 아래 경로를 **가정값**으로 적되 코드에는 `shared/config`의 AI 경로 상수로만 둔다.

| 동작      | AI 서버 원본 경로                       | 프론트가 부를 것으로 가정한 경로                      |
| --------- | --------------------------------------- | ----------------------------------------------------- |
| 열람      | `GET /api/ai/v1/wiki`                   | `GET /api/v1/ai/wiki` **(미확정)**                    |
| 논지 수정 | `PUT /api/ai/v1/wiki/theses/{ticker}`   | `PUT /api/v1/ai/wiki/theses/{stockCode}` **(미확정)** |
| 사실 삭제 | `DELETE /api/ai/v1/wiki/facts/{factId}` | `DELETE /api/v1/ai/wiki/facts/{factId}` **(미확정)**  |

경로 파라미터 이름도 미확정이다. AI 원본은 `ticker`이고 프론트 규약은 `stockCode`인데(§2), 중계 경로의 파라미터 이름을 지목한 문서가 없다. 위 표의 `{stockCode}`는 프론트 규약을 밀어 넣은 가정이다.

**진입 경로.** 확정 근거가 없다. 후보와 판단 근거만 적는다.

| 후보                       | 근거                                                                                                                                 | 문제                                                            |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------- |
| 마이페이지 하위 `/my/wiki` | 마이페이지가 "프로필·계좌 리셋·회차 조회 진입"을 모은 **사용자 자신에 관한 화면**이다(§1 기타). 하단 탭 4개를 늘리지 않아도 된다(§3) | 마이페이지가 계좌 관리 화면으로 읽혀 AI 맥락이 눌린다           |
| AI 채팅 안에서 진입        | 맥락을 **모으는 곳이 대화**다(AI 명세 §9). 고친 직후 다음 질문으로 확인하는 흐름이 짧다                                              | 대화 화면에 전체 화면 전환을 붙이면 대화 스크롤 위치가 날아간다 |
| 하단 탭 5번째              | 발견성이 가장 높다                                                                                                                   | **채택하지 않는다.** 터치 영역 44×44px 기준을 깬다(§3)          |

**잠정으로 마이페이지 하위(`/my/wiki`)를 쓰고, AI 채팅 상단에 보조 진입 링크를 둔다.** 라우트를 `/my` 하위에 두면 나중에 진입 지점을 옮겨도 라우트를 유지할 수 있다. 근거가 얇으므로 와이어프레임 리뷰에서 다시 본다.

**표시할 것.** `GET /wiki` 응답에 실제로 있는 것만이다 (근거: `ai/docs/api-spec.md` §9의 `GET /api/ai/v1/wiki` 응답 예시).

| 영역               | 필드                   | 화면 표기                                                                                                                                                                                                    |
| ------------------ | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

**응답 본문 자체가 미확정이다.** `openapi.json`의 `GET /api/ai/v1/wiki`는 `Envelope[dict]`, 즉 `content`가 `additionalProperties: true`인 빈 object로 떨어진다. 위 표는 AI 명세 §9의 예시에서 읽은 것이라 계약이 아니다. Zod 스키마는 **필드가 없으면 그 표기만 생략하는 방향**으로 느슨하게 짜고 스키마 에러로 화면을 죽이지 않는다.

**편집·삭제 동작.**

- **논지 수정** — 행을 눌러 텍스트 편집(최대 500자, `openapi.json` `ThesisIn.text`). 저장하면 `PUT .../theses/{stockCode}`. 수정하면 `source`가 자동으로 `user_stated`가 된다(AI 명세 §9). 화면이 `source`를 직접 보내지 않는다
- **사실 삭제** — 행의 삭제로 `DELETE .../facts/{factId}`. "즉시 이후 모든 응답에서 제외된다"가 명세에 있으므로(AI 명세 §9) 되돌리기를 만들지 않고 **삭제 확인을 받는다**
- **논지에는 삭제 경로가 없다.** `DELETE`는 `facts` 전용이다. 논지 행에는 수정만 둔다. 미확정 항목으로 올렸다
- **갱신 방식(낙관적 갱신 vs 재조회)을 지금 정하지 않는다.** `PUT`·`DELETE`의 응답 본문이 미확정이라(contracts 미확정 "`wiki`·`feedback` 응답 스키마", 이슈 #13 3번) 응답이 갱신된 항목을 돌려주는지 빈 봉투인지 모른다. 결정은 회신 후로 미루고, 그때까지 **성공 응답을 무시하고 `GET /wiki`를 재조회**한다. 되돌릴 범위가 쿼리 무효화 한 줄이라 가장 싸다
- 사용자 편집이 6종 응답에 **언제 반영되는지도 미확정**이다. `DELETE`만 "즉시"라고 적혀 있고 `PUT`은 없으며, 명세는 위키 갱신을 "대화 종료 후 비동기 배치"로 못박고 있다. "반영까지 시간이 걸립니다" 문구를 넣을지 정할 수 없다

**빈 상태.** 위키는 **처음에 반드시 비어 있다.** 사실도 논지도 AI가 대화·거래에서 누적해야 생긴다.

- `profile`·`theses`가 둘 다 비면 화면 전체를 빈 상태로 두고 **AI 채팅으로 보내는 버튼**을 놓는다. 맥락은 대화에서만 쌓인다
- 한쪽만 비면 그 섹션에만 빈 문구를 둔다. 논지 쪽 빈 문구는 "종목을 매수하면 AI가 대화에서 이유를 묻습니다" 취지로 **수집 경로를 알려주는 문구**여야 한다. 입력 폼을 주지 않는다
- 빈 배열을 실패로 다루지 않는다(contracts "구현 현황이 만드는 제약"과 같은 원칙)

### 기타

| 화면       | 라우트 | 목적                                        | 필요한 API                                                                         | AI  | 티켓                                                    | 의존   |
| ---------- | ------ | ------------------------------------------- | ---------------------------------------------------------------------------------- | --- | ------------------------------------------------------- | ------ |
| 마이페이지 | `/my`  | 프로필, 계좌 리셋, 회차 조회 진입, 로그아웃 | `GET /api/v1/users/me` · `POST /api/v1/account/reset` · `POST /api/v1/auth/logout` |     | [3-8](https://ssafy.atlassian.net/browse/S15P21A101-60) | 로그인 |
| 404        | `*`    | 없는 경로                                   | —                                                                                  |     | —                                                       | —      |

- 이전 판의 `설정 /settings`를 **마이페이지로 흡수했다.** 테마·로그아웃만 있는 화면과 계좌 리셋 화면을 따로 두면 사용자가 어느 쪽에 무엇이 있는지 외워야 한다.
- **계좌 리셋은 확인 팝업 필수**다. 문구는 명세가 고정했다 — "현재 보유 종목과 예수금이 초기화됩니다. 기존 기록은 열람만 가능합니다." (기능명세 §2.3)
- 리셋은 원장을 지우지 않는다. 현재 회차를 종료하고 새 회차를 열며 예수금 1,000,000원을 다시 지급한다. **누적 충전 한도도 함께 초기화된다.**

**화면 17개.** 인증 2 · 홈/자산 5 · 탐색/거래 6 · AI 2 · 기타 2.

## 2. 라우트 트리와 URL 상태

```
/                              홈
/login                         로그인 (카카오 인가 진입)
/oauth/kakao                   카카오 콜백 (인가 코드 → 토큰 교환)
/search                        종목 검색 (초기 상태 = 최근 검색어)
/recent                        최근 본 종목
/stocks/:stockCode             종목 상세
/stocks/:stockCode/order       주문
/portfolio                     포트폴리오
/transactions                  매매 내역
/rounds                        회차 조회
/deposit                       충전
/watchlist                     관심 종목
/chat                          AI 채팅
/my                            마이페이지
/my/wiki                       AI가 이해한 나 (위키) — 진입 경로 잠정
*                              404
```

**종목코드 경로 파라미터는 `:stockCode`로 통일한다.** 백엔드 명세 전체가 `stockCode`를 쓰고 AI 명세만 `ticker`를 쓰는데, 프론트는 백엔드만 호출하므로 `stockCode`를 따른다. 이름이 두 개면 파라미터 추출부에서 조용히 `undefined`가 된다.

**`/stocks/:stockCode`와 `?tab=ai`는 이 문서 밖에서도 쓰인다.** 브리핑 응답의 `deeplink`가 이 경로 문자열을 **AI 서버에서 직접 만들어** 내려보낸다 (AI 명세 §8 예시 `"/stocks/000660?tab=ai"`).
라우트는 보통 프론트 혼자 정하는 값이지만 이 둘만은 아니다. **바꾸면 브리핑 링크가 조용히 404가 된다.** 화면에서는 에러도 안 뜨고 그냥 빈 페이지로 간다. 바꿔야 하면 AI 파트에 먼저 알린다.

**화면 이름도 마찬가지다.** 채팅 요청의 `context.screen`이 `home · portfolio · stock_detail · order · chat` **열거값**이다(AI 명세 §6). 사용자가 "이거 어때?"처럼 대명사로 물을 때 AI가 지시 대상을 푸는 데 쓴다.
그래서 **채팅은 `/chat` 전용 화면만이 아니다.** 위 네 화면에서 열면 `screen`과 `ticker`를 실어 보내고, 그래야 종목 상세에서 "이거"가 그 종목으로 해소된다. 맥락 없이 열면 AI가 되물어야 해서 대화가 한 번 더 왕복한다.

### 쿼리 파라미터로 둘 상태

컨벤션 §4가 "새로고침·공유·뒤로가기에서 살아 있어야 하는 것은 전부 URL"이라고 정했다.
모바일에서는 뒤로가기를 훨씬 자주 쓰므로 탭 선택을 `useState`에 두면 바로 티가 난다.

| 경로                       | 파라미터   | 값                                      |
| -------------------------- | ---------- | --------------------------------------- |
| `/stocks/:stockCode`       | `tab`      | `chart` \| `info` \| `ai`               |
| `/stocks/:stockCode`       | `period`   | `1M` \| `3M` \| `1Y` (전부 일봉)        |
| `/stocks/:stockCode/order` | `side`     | `buy` \| `sell`                         |
| `/portfolio`               | `tab`      | `holdings` \| `diagnosis`               |
| `/portfolio`               | `sort`     | `EVALUATION` \| `PROFIT_RATE`           |
| `/transactions`            | `type`     | `ALL` \| `BUY` \| `SELL` \| `DEPOSIT`   |
| `/transactions`            | `roundId`  | 회차 번호. 생략하면 활성 회차           |
| `/watchlist`               | `sort`     | `REGISTERED` \| `NAME` \| `CHANGE_RATE` |
| `/search`                  | `q`        | 검색어                                  |
| `/login`                   | `redirect` | 로그인 후 돌아갈 경로                   |

차트 기간 값은 `GET /stocks/{stockCode}/candles`의 `period`와 같은 문자열을 쓴다. 분봉 도입 여부는 미확정(S0-4)이므로 `1D`·`1W`는 지금 넣지 않는다. **탭 구성은 데이터가 정해진 뒤에 늘린다.**

**주문 입력값(수량)은 URL에 두지 않는다.** 공유될 값이 아니고, 잘못 공유되면 남의 주문 화면이 채워진 채 열린다.

## 3. 화면 간 이동

### 하단 탭바 — 4개

```
홈  |  탐색  |  포트폴리오  |  AI
/      /search   /portfolio    /chat
```

탭을 5개 이상 두면 모바일에서 터치 영역이 좁아진다(컨벤션 §9의 44×44px 기준).
관심 종목·최근 본 종목·매매 내역·충전·마이페이지는 탭에 두지 않고 홈·포트폴리오·탐색 안에서 들어간다.

### 주요 흐름

```
로그인 → 카카오 인가 → /oauth/kakao → 홈
홈 → 보유 종목 → 종목 상세 → 주문 → 체결 → 매매 내역
탐색 → 최근 검색어·최근 본 종목 → 검색 → 종목 상세 → 관심 종목 담기
포트폴리오 → 진단 탭 → (AI 진단 결과) → 종목 상세
주문 → 예수금 부족 → 충전 → 주문으로 복귀
마이페이지 → 계좌 리셋 → (확인 팝업) → 새 회차 홈
마이페이지 → 회차 조회 → 과거 회차 매매 내역
AI 채팅 → 답변 속 종목 언급 → 종목 상세
마이페이지 → AI가 이해한 나 → (논지 수정 · 사실 삭제) → AI 채팅으로 확인
종목 상세 tab=ai → 논지 유도 카드 → AI 채팅(맥락 동반) → 답변 → 종목 상세로 복귀
```

**마지막 흐름이 기획서의 "왜 사는지"를 완성한다.** 논지는 화면 입력 폼이 아니라 대화로만 기록되므로(§1 위키), 종목 상세에서 채팅으로 가는 길과 **돌아오는 길**이 둘 다 있어야 한다. 편도로 만들면 사용자가 보던 종목을 잃는다.

**종목 상세가 허브다.** 거의 모든 화면에서 여기로 들어온다.
그래서 종목 상세는 진입 경로와 무관하게 혼자 성립해야 한다 — 이전 화면의 상태를 props로 받아 쓰지 않는다.

### 주문을 별도 라우트로 둔 이유

토스증권은 주문을 바텀시트로 띄운다. 그런데 주문은 **뒤로가기로 빠져나갈 수 있어야 하고**, 실패했을 때 되돌아올 지점이 필요하다.
라우트로 두면 뒤로가기가 자연스럽게 처리되고 `redirect` 파라미터로 로그인 후 복귀도 된다.
화면 표현은 바텀시트로 하되 **주소는 갖는다.** 충전 화면도 같은 이유로 라우트를 갖는다 — 주문 도중 예수금이 모자라 충전으로 갔다가 돌아와야 한다.

## 4. AI 슬롯 배치

AI 명세는 "화면에서 AI 응답이 들어갈 빈 슬롯"만 요구한다. 위치는 프론트가 정한다.

**6종 전부 일반 요청/응답이다. 스트리밍이 아니다.**
`ai/docs/openapi.json`의 6개 엔드포인트가 모두 단일 JSON(`Envelope`)을 반환한다.

| #   | 기능             | 화면            | 위치                         | 경로 (프론트가 호출하는 것)                              |
| --- | ---------------- | --------------- | ---------------------------- | -------------------------------------------------------- |
| 1   | 데일리 브리핑    | 홈              | 자산 요약 아래 첫 블록       | `GET /api/v1/ai/briefing` **(잠정)**                     |
| 2   | 수익률 원인 분석 | 홈 · 포트폴리오 | 손익 숫자 바로 아래          | `POST /api/v1/ai/portfolio/attribution` **(잠정)**       |
| 3   | AI 종목 분석     | 종목 상세       | `tab=ai` 탭                  | `POST /api/v1/ai/stocks/{stockCode}/analysis` **(잠정)** |
| 4   | 주문 전 점검     | 주문            | 주문 확인 단계, 제출 버튼 위 | `POST /api/v1/ai/orders/preview` **(잠정)**              |
| 5   | 포트폴리오 진단  | 포트폴리오      | `tab=diagnosis` 탭           | `POST /api/v1/ai/portfolio/diagnosis` **(잠정)**         |
| 6   | Ask My Portfolio | AI 채팅         | 화면 전체                    | `POST /api/v1/ai/chat` **(잠정)**                        |

### 기획서의 기능 6개와 이 슬롯 6종은 1:1이 아니다

개수가 같아 짝이 맞아 보이지만 **세는 단위가 다르다.** 기획서 §주요 기능 "AI 투자 도움"은 사용자가 체감하는 기능 단위이고, 위 표는 호출할 엔드포인트 단위다.
**기획서 항목마다 슬롯을 만들면 없는 API를 부르게 된다.** 화면을 그리기 전에 이 대응을 먼저 본다.

| 기획서 "AI 투자 도움"      | 프론트가 실제로 부르는 것                               | 슬롯 |
| -------------------------- | ------------------------------------------------------- | ---- |
| 내 종목 맞춤 데일리 브리핑 | `GET /ai/briefing` 1회                                  | 1    |
| 뉴스 기반 종목 영향 분석   | `POST /ai/stocks/{stockCode}/analysis` **의 일부 섹션** | 3    |
| 기업 분석                  | **같은 요청의 다른 섹션**                               | 3    |
| 매수 전 근거·리스크 점검   | `POST /ai/orders/preview`                               | 4    |
| 포트폴리오 진단            | `POST /ai/portfolio/diagnosis`                          | 5    |
| 수익률 원인 분석           | `POST /ai/portfolio/attribution`                        | 2    |

**뉴스 분석과 기업 분석은 요청도 화면도 하나다.** 둘 다 같은 종목의 같은 RAG를 읽으므로 AI 파트가 엔드포인트 하나로 합쳤다(AI 명세 §2). 종목 상세 `tab=ai` 안에 탭을 두 개 만들지 않는다.
기획서 §개인화 AI의 "종목별 투자 논리 기록 및 관리"도 독립 기능이 아니다 — 같은 응답의 `thesis_check` 섹션과 위키 화면(§1)으로 나뉜다.

### ★ 기획서가 굵게 짚은 넷 — 화면에서 눌리면 안 되는 것

기획서 §타겟분석 표는 해결 방향 여섯 줄 중 **네 개만 굵게** 표시했다. 나머지는 어느 모의투자 앱에나 있고, **이 넷이 없으면 이 서비스를 만들 이유가 없다.**
슬롯을 다 채워도 이 넷이 화면에서 접히거나 뒤로 밀리면 기획이 구현되지 않은 것이다. 각각이 어디로 가는지 먼저 못박는다.

| 기획서가 굵게 쓴 것                                | 나타나는 곳                                  | 상세             |
| -------------------------------------------------- | -------------------------------------------- | ---------------- |
| **"현재 가격이 왜 비싸거나 싼지" 중심으로 설명**   | 3번 슬롯 `current` 섹션                      | 아래 3번 슬롯    |
| **공시·실적·시장 데이터 기반으로 교차 확인**       | **슬롯 6종 전부** — 근거 목록                | 아래 "근거 표시" |
| **"왜 사는지"를 AI가 질문하고 투자 논리를 기록**   | 3번 슬롯 `thesis_check` + AI가 이해한 나(§1) | 아래 3번 슬롯    |
| **쏠림 · 주요 리스크 · 반대 근거를 한 번 더 점검** | 4번 슬롯 전체                                | 아래 4번 슬롯    |

**넷 중 셋이 3·4번 슬롯에 몰려 있다.** 종목 상세 `tab=ai`와 주문 화면이 기획의 핵심이고 나머지 화면은 거기까지 데려가는 경로다.
일정이 밀리면 **이 두 화면을 마지막까지 지킨다.** 브리핑·진단은 늦출 수 있지만 이 둘은 빠지면 남는 게 평범한 모의투자 앱이다.

#### 3번 슬롯 — 종목 분석은 섹션 7개다

`openapi.json`의 `AnalysisSections`가 돌려주는 7개다. **표시 순서는 화면이 정한다** — 응답은 객체라 순서가 없다.

| 섹션           | 화면 제목 (AI가 보낸 `title` 그대로) | 기획서 대응                                  | `null`이 되는 조건                   |
| -------------- | ------------------------------------ | -------------------------------------------- | ------------------------------------ |
| `current`      | 현재 상태                            | 기업 분석 — 사업·수익 구조, 실적, 밸류에이션 | 요청에서 뺐을 때만                   |
| `changes`      | 최근 변화                            | 뉴스 분석 — 뉴스 핵심 내용 요약              | 요청에서 뺐을 때만                   |
| `attention`    | 시장이 주목하는 요인                 | 뉴스 분석 — 주가 **긍정** 요인               | 요청에서 뺐을 때만                   |
| `risks`        | 확인된 위험 요인                     | 뉴스 분석 — 주가 **부정** 요인, 주요 리스크  | 요청에서 뺐을 때만                   |
| `my_impact`    | 내 계좌 영향                         | 뉴스 분석 — 기업 실적·사업 영향              | `personalize: false` 또는 **미보유** |
| `thesis_check` | 논지 점검                            | 개인화 AI — 투자 논리 기록·관리              | 기록된 활성 논지가 없을 때           |
| `next_events`  | 다가오는 일정                        | 브리핑 — 시장 주요 일정                      | 없음 (일정이 없으면 빈 배열)         |

**섹션 제목을 화면이 짓지 않는다.** 기획서는 "주가 긍정·부정 요인 분석"이라고 적었지만 AI 명세 §2는 그 표현을 **금지한다** — "긍정 요인 / 부정 요인"이 의견 제시로 읽히므로 "시장이 주목하는 요인 / 공시·실적에서 확인된 위험 요인"이라는 출처 귀속형으로 고정했다. 규제 대응이라 화면에서 되돌리면 안 된다. 목표주가·투자의견은 어떤 섹션에도 오지 않는다.

- **★ `current`에 기획서의 차별점이 걸려 있다.** 기획서는 "PER/PBR·실적·성장률 등을 어려운 용어 대신 **현재 가격이 왜 비싸거나 싼지** 중심으로 설명"이라고 굵게 적었다. 그래서 **화면이 지표 표를 따로 만들지 않는다** — PER·PBR을 숫자로 나열하는 순간 기획서가 피하려던 화면이 그대로 나온다. AI가 보낸 `text`를 문장으로 두고 숫자 강조는 `segments`로만 한다
- **★ `thesis_check`가 "왜 사는지"의 종착점이다.** `null`이면 그 자리에 **논지 입력 유도 카드**를 둔다. 입력 폼이 아니라 **AI 채팅으로 보내는 버튼**이다(AI 명세 §9 수집 경로). 논지는 대화에서만 기록된다
- **요청 파라미터가 둘이다.** `sections`(배열, 생략하면 전체)와 `personalize`(기본 `true`). 비보유 종목에 `my_impact`·`thesis_check`를 요청해도 에러가 아니라 `null`이다
- **`null` 섹션은 자리를 비운다.** 접힌 카드나 "정보 없음" 박스를 만들지 않는다. 미보유 종목에서 두 개가 빠지는 것이 정상 상태다
- 섹션마다 `cached`·`cached_at`이 온다. `current`·`changes`·`attention`·`risks`·`next_events`는 **종목 단위 6시간 캐시**라 다른 사용자와 같은 값이고, `my_impact`·`thesis_check`만 요청마다 생성된다
- **피드백 슬롯은 섹션이 7개여도 탭 하단 하나다.** `requestId`는 응답 하나에 하나다(아래 피드백 규칙)

#### 1번 슬롯 — 브리핑은 블록 하나에 항목 최대 4건이다

기획서가 브리핑 아래 네 줄로 적은 것(핵심 뉴스 선별 · 종목별 이슈 요약 · 시장 일정 · 포트폴리오 영향 종합)은 **블록 4개가 아니라 항목의 종류다.** `BriefingContent.items[]`의 `category`로 구분되고 `holding_move` · `earnings` · `filing` · `macro_event` · `portfolio_shift` 5종이며 **최대 4건**이 온다(AI 명세 §8).

- 홈에는 **블록 하나**를 두고 그 안에 항목을 `rank` 순으로 쌓는다. 종류별로 블록을 나누면 어떤 날은 빈 블록이 생긴다
- `related_tickers`로 종목 상세 링크를 만든다
- **`deeplink`는 AI 서버가 만든 프론트 경로 문자열이다** (예시: `/stocks/000660?tab=ai`). 화면이 조립하지 않고 그대로 이동시킨다 — §2에 결합 관계를 적었다

#### 4번 슬롯 — 주문 전 점검은 세 덩어리다

기획서가 굵게 쓴 "**내 포트폴리오 쏠림, 주요 리스크, 반대 근거를 한 번 더 점검**"이 응답의 세 필드에 그대로 대응한다.
**셋 중 하나라도 빠뜨리면 이 슬롯을 만든 이유가 없어진다.** 다른 슬롯은 정보를 주지만, 이 슬롯만 **사용자를 멈춰 세우는 것**이 목적이다.

| 기획서 표현            | 응답 필드                    | 화면                                                             |
| ---------------------- | ---------------------------- | ---------------------------------------------------------------- |
| 내 포트폴리오 **쏠림** | `before` · `after` · `delta` | 주문 전후 비교. 지표 12개가 오지만 **전부 보여주지 않는다**      |
| **주요 리스크**        | `warnings[]`                 | `severity` 순. `metric`·`threshold`·`before`·`after`가 함께 온다 |
| **반대 근거**          | `thesis_conflicts[]`         | 이 주문이 내가 기록한 논지와 어긋날 때만                         |

- **★ `thesis_conflicts`가 이 슬롯에서 가장 중요하다.** 기획서의 "반대 근거"가 이것 하나다. 남이 반대하는 게 아니라 **사용자 자신이 과거에 기록한 논지**(`fact` · `recorded_at`)를 다시 보여주는 것이므로, 논지 원문과 기록 시점을 반드시 함께 노출한다. `conflict` 문구만 띄우면 "AI가 내 주문에 반대한다"로 읽히고 기획 의도가 뒤집힌다
- 배열이 비면 그 덩어리를 통째로 감춘다. 논지를 기록한 적이 없으면 항상 비어 있고 그것이 정상이다
- **지표 12개를 전부 노출하지 않는다.** `warnings[].metric`이 지목한 것과 `delta`가 큰 것만 고른다. 기획서 §디자인 컨셉의 "글자 크고 명확하게, 작은 보조정보 최소화"가 40~60대 타겟에서 온 요구다
- **`feasible: false`면 `shortfall`(모자란 금액)이 온다.** 이 숫자를 그대로 충전 화면으로 넘긴다 — §3의 "주문 → 예수금 부족 → 충전 → 주문 복귀" 흐름이 여기서 시작된다
- **승인·거절을 표시하지 않는다.** AI 명세 §7이 "판단은 하지 않는다"로 못박았다. 경고가 있어도 주문 버튼을 막지 않는다. 버튼을 막는 것은 `GET /orders/available`뿐이다(§1)

### 경로가 `(잠정)`인 이유

**호출 경로 자체는 확정이다 — 프런트 → 백엔드 → AI.** 프론트는 `/api/v1` 하나만 쓰고 AI 서버(`/api/ai/v1`)를 직접 부르지 않는다.
확정되지 않은 것은 **백엔드가 AI를 중계할 때 붙일 경로 문자열**이다. 어느 문서에도 아직 없다.
위 표는 AI 원본 경로를 백엔드 Base URL 아래로 옮긴 형태를 가정한 값이다.

되돌리는 비용을 작게 두기 위해 **AI 경로 문자열은 `shared/config` 상수 한 곳에 모은다.** 회신이 오면 그 파일만 고친다.

### 슬롯 공통 규약

- 슬롯은 **위젯 단위 에러 경계**를 갖는다(컨벤션 §8). AI가 실패해도 그 화면의 나머지는 살아 있어야 한다
- 슬롯이 비어 있는 상태(아직 요청 전)와 로딩 상태를 구분해 표시한다
- 2번은 홈과 포트폴리오 양쪽에 들어간다. **컴포넌트를 두 번 만들지 않는다** — 한쪽 feature에 두고 다른 쪽이 재사용하거나, 겹치면 `shared`로 올린다
- AI 응답의 `data_as_of`·`disclaimer`는 화면 노출 대상이지만 백엔드 중계 후에도 남아 있을지 확인되지 않았다. **Zod 스키마에서 optional로 두고, 없으면 그 표기만 생략한다.** 스키마 에러로 슬롯을 죽이지 않는다
- **프론트는 AI 응답을 조립하지 않는다.** 수치 치환·검증은 AI 서버가 끝낸 상태로 온다
- **문장은 `text` 하나면 렌더된다.** 같이 오는 `segments[]`는 `text`를 잘라 놓은 것일 뿐 다른 정보가 아니라, 이어 붙이면 `text`와 정확히 일치한다(AI 명세 §2.3). **등락 색·강조가 필요할 때만 순회한다** — `segments[].direction`이 `up`/`down`이고 국내 관례대로 적색·청색이다. 숫자를 정규식으로 찾아 칠하지 않는다
- **캐릭터(핀치·블루치)가 나올 수 있는 자리는 이 슬롯들과 그 빈 상태·에러 자리뿐이다.** 기획서 §캐릭터가 "핵심 금융 정보나 매매 영역에는 X, AI가 설명·안내하는 순간에만"으로 역할을 제한했다. 자산 요약 숫자, 주문 확인 단계, 충전 확인 단계에는 넣지 않는다. **4번 슬롯이 예외처럼 보이지만 아니다** — 캐릭터가 허용되는 범위는 점검 블록 안까지이고, 제출 버튼 주변은 매매 영역이다

### ★ 근거 표시 — 기획서의 "교차 확인"이 화면에 나오는 방식

기획서가 굵게 쓴 "**공시·실적·시장 데이터 기반으로 교차 확인**"은 화면에서 근거 목록(`citations`) 하나로 나타난다.
**이 목록이 없으면 AI 답변과 유튜브 추천이 화면에서 구별되지 않는다.** 타겟을 "지인·카페·유튜브 의존"에서 꺼내는 것이 기획 의도이므로 접어두거나 생략하지 않는다.

`citations`는 응답 봉투의 최상위 키라 **슬롯 6종 전부에 실린다.** 근거가 없는 응답에서는 빈 배열이다.

| 필드                  | 화면                                                                                                                                            |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `type`                | `filing`(DART 공시) · `financial`(재무제표) · `news` · `price` · `macro`(ECOS) · `engine`(자체 계산) · `wiki`(내 논지) 7종. **뱃지로 구분한다** |
| `title` · `publisher` | 근거 제목과 발행처                                                                                                                              |
| `url`                 | 원문 링크. **`engine`·`wiki`에는 없다** — 링크 없는 행을 눌리게 만들지 않는다                                                                   |
| `published_at`        | 언제 자료인지. 공시·뉴스는 시점 자체가 신뢰도다                                                                                                 |
| `snippet`             | 발췌. 길면 접는다                                                                                                                               |
| `relevance`           | 0~1. **정렬에만 쓰고 숫자로 노출하지 않는다** — 사용자가 해석할 수 없는 값이다                                                                  |

- 본문은 `[^cit_2]` 형태로 참조한다(AI 명세 §2.4). **각주를 눌러 목록으로 보내는 것까지만 한다.** hover 툴팁 미리보기를 만들지 않는다 — 모바일에 hover가 없다
- **`engine`은 외부 URL이 없는 자체 계산이다.** 공시·뉴스 뱃지와 같은 모양으로 두면 "출처가 있는 척"이 된다. 시각적으로 구분한다
- **`wiki`는 사용자 자신이 기록한 논지다.** 외부 근거처럼 보이면 안 된다
- 빈 배열이어도 슬롯을 실패로 다루지 않는다. 근거 영역만 감춘다

### 피드백 슬롯 배치 규칙

`POST /api/v1/ai/feedback`은 **화면 목록이 아니라 규칙으로 적는다.** 화면마다 따로 적으면 AI 기능이 늘거나 줄 때 어긋난다.
이 경로는 `apiSpec.md` §10.1 표에 **있다** — 위키 3종과 달리 중계 경로가 확정된 항목이다.

**규칙 하나로 요약하면: `requestId` 하나 = 피드백 슬롯 하나.**

피드백은 화면 단위도 섹션 단위도 아니고 **AI 응답 1건 단위**다. `POST /feedback`이 `request_id`로 원본 응답을 찾기 때문에(AI 명세 §10, apiSpec §10.3) 슬롯을 응답보다 잘게 쪼개면 어느 `requestId`를 실을지 정할 수 없고, 굵게 묶으면 여러 응답의 평가가 한 값으로 뭉개진다.

붙는 자리는 **그 응답 블록의 마지막 요소**다. `dataAsOf`·`disclaimer` 표기 아래에 온다.

| #   | 기능             | 화면            | 피드백이 붙는 자리                                                                                                                                    |
| --- | ---------------- | --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 데일리 브리핑    | 홈              | 브리핑 블록 하단. 브리핑 응답 1건 = 슬롯 1개 (`items[]`마다가 아니다)                                                                                 |
| 2   | 수익률 원인 분석 | 홈 · 포트폴리오 | 원인 분석 블록 하단. **컴포넌트가 하나이므로 슬롯도 하나다.** 두 화면이 각자 요청하면 `requestId`가 달라지므로 슬롯은 응답을 받은 그 화면의 것을 쓴다 |
| 3   | AI 종목 분석     | 종목 상세       | `tab=ai` 탭 최하단. **섹션(`current`·`risks` 등)마다 붙이지 않는다** — `requestId`가 응답 단위다                                                      |
| 4   | 주문 전 점검     | 주문            | 점검 블록 하단, **제출 버튼 위쪽 영역 안**. 제출 버튼과 붙여 놓지 않는다. 주문 확인 단계에서 오탭하면 주문이 나간다                                   |
| 5   | 포트폴리오 진단  | 포트폴리오      | `tab=diagnosis` 탭 최하단                                                                                                                             |
| 6   | Ask My Portfolio | AI 채팅         | **AI 답변 말풍선마다 하나.** 답변마다 `requestId`가 다르다. 화면 하단에 하나만 두면 어느 답변에 대한 평가인지 잃는다                                  |

#### 에러 자리의 피드백

에러 봉투에도 `requestId`가 보존되므로(apiSpec §10.3) 실패 응답과 `INSUFFICIENT_DATA` 대체 문구 자리에도 붙는다.
성공 자리와 다른 점은 셋이다.

1. **재시도와의 우선순위가 갈린다.** `apiSpec.md` §10.4의 분류를 그대로 쓴다
   - 재시도 가능(`RETRIEVAL_FAILED` 502 · `LLM_TIMEOUT` 504 · `AI_UPSTREAM_UNAVAILABLE` 502 · `AI_UPSTREAM_TIMEOUT` 504) — **재시도 버튼이 주 동작**이고 피드백은 보조로 접어 둔다
   - 재시도 무의미(`INSUFFICIENT_DATA` 409 · `GUARDRAIL_BLOCKED` 422) — 재시도 버튼을 만들지 않으므로 **피드백이 그 자리에서 유일한 사용자 행동**이다. 가장 크게 노출된다
2. **`rating: "up"`을 노출하지 않는다 (잠정).** 실패한 응답에 "좋다"를 표시할 대상이 없다. `rating`은 `up`·`down` 중 하나가 필수인 값이므로(`openapi.json`의 `FeedbackRating`) 에러 자리는 `down` 고정으로 보낸다. 근거 문서가 없는 프론트 판단이다
3. **`requestId`가 없으면 슬롯을 만들지 않는다.** §10.3이 보존을 약속한 것은 AI가 돌려준 에러다. 백엔드가 AI에 도달하지 못해 자기가 만든 `AI_UPSTREAM_*`에 `requestId`가 실리는지는 미확정이다. 슬롯을 조건부로 짠다

| 필드         | 필수       | 값                                                                                                            | 화면                                                     |
| ------------ | ---------- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| `request_id` | 필수       | 평가 대상 응답의 `requestId`                                                                                  | 사용자가 입력하지 않는다. 응답에서 들고 온다             |
| `rating`     | 필수       | `up` 또는 `down`                                                                                              | 엄지 두 개. 에러 자리는 `down` 고정                      |
| `reasons`    | 선택(배열) | `wrong_number` · `not_relevant` · `outdated` · `too_generic` · `unclear` · `wrong_citation` **6종 복수 선택** | `down`을 누른 뒤에만 펼친다. `up`에는 사유를 묻지 않는다 |
| `comment`    | 선택       | 자유 텍스트, **최대 1000자** (`FeedbackIn.comment.maxLength`)                                                 | 선택 입력. 필수로 만들지 않는다                          |

**요청 본문 키의 표기가 미확정이다.** `apiSpec.md` §10.3이 정한 camelCase 재포장은 **응답**에 관한 규칙이고, 중계 요청 본문을 `requestId`로 보내는지 `request_id`로 보내는지 지목한 문서가 없다. 위 표는 AI 원본 필드명이다.

#### 전송 후 UI

**확정으로 적지 않는다.** `POST /feedback`의 응답 본문이 미확정이고(contracts 미확정 항목 "`wiki`·`feedback` 응답 스키마", 이슈 #13 4번), 같은 `requestId`로 두 번 보낼 때 덮어쓰는지 누적되는지도 정해지지 않았다.
그래서 **되돌릴 수 있는 쪽으로만 만든다** — 전송에 성공하면 그 슬롯을 "보냈습니다" 상태로 바꾸고 다시 누를 수 없게 잠근다. 수정·취소를 만들지 않는다. 회신이 오면 잠금을 푸는 것은 쉽고, 반대 방향(수정 가능하게 먼저 만들었다가 중복이 문제로 드러나는 것)은 되돌리기 어렵다.

## 5. 화면 ↔ feature 매핑

컨벤션 §2의 `features/` 구조에 대응시킨다. **feature는 라우트가 아니라 도메인 단위로 나눈다.**

| feature     | 담당 화면                                   | 주요 내용                                             |
| ----------- | ------------------------------------------- | ----------------------------------------------------- |
| `auth`      | 로그인, 카카오 콜백                         | OAuth 진입·교환, 토큰, 라우트 가드                    |
| `home`      | 홈                                          | 자산 요약, 브리핑 슬롯                                |
| `stock`     | 검색, 최근 검색어, 최근 본 종목, 종목 상세  | 종목 정보, 시세, 차트, 종목 분석 슬롯                 |
| `order`     | 주문, 매매 내역                             | 주문 폼, 검증, 주문 전 점검 슬롯                      |
| `portfolio` | 포트폴리오                                  | 보유 종목, 손익, 진단 슬롯, 원인 분석 슬롯            |
| `chat`      | AI 채팅                                     | 대화 목록, 질문 전송                                  |
| `watchlist` | 관심 종목                                   | 담기·해제, 목록                                       |
| `account`   | 충전, 마이페이지, 회차 조회, AI가 이해한 나 | 한도, 모의 결제, 계좌 리셋, 회차 목록, 위키 열람·수정 |

### 여러 feature가 필요한 것 → `shared`

- 시세 구독 관리자 — `stock` `home` `portfolio` `watchlist`가 전부 쓴다
- 종목 시세 표시 컴포넌트(종목명 + 현재가 + 등락률 + 거래정지 뱃지) — 검색·최근 본 종목·관심 종목·포트폴리오에서 반복된다
- 금액·비율·등락 포매터 — **등락률 변환은 이 함수 하나만 거친다.** 컴포넌트에서 직접 계산하지 않는다
- 멱등성 키 생성 유틸 — 충전과 주문이 함께 쓴다
- AI 경로 상수와 AI 응답 봉투 어댑터
- **AI 피드백 슬롯 컴포넌트** — AI 응답이 렌더되는 자리 전부에 붙는다. `requestId` 하나만 받아 동작하므로 feature에 두면 여섯 곳에서 재구현된다

**시세 구독 관리자와 종목 행 컴포넌트가 가장 자주 재구현될 후보다.** 분담 전에 한 명이 먼저 만든다.

## 6. 분담 후보 묶음

두 덩이로 묶었다. 기준은 셋이다 — **AI 슬롯이 한쪽에 몰리지 않을 것, 학습 부담이 갈릴 것, feature 폴더가 겹치지 않을 것.**

발행된 티켓의 담당자 가배정과 맞춘다 (돈 흐름 = 김채은, 시세 = 유승주).

### A · 시세 축

| 화면                    | feature     | 티켓     |
| ----------------------- | ----------- | -------- |
| 종목 검색 · 최근 검색어 | `stock`     | 1-8      |
| 최근 본 종목            | `stock`     | 1-8      |
| 종목 상세 · 차트        | `stock`     | 1-8, 2-9 |
| 관심 종목               | `watchlist` | 2-9      |
| 마이페이지 · 회차 조회  | `account`   | 3-8      |
| AI가 이해한 나 (위키)   | `account`   | 미발행   |

AI 슬롯 1종(종목 분석).
기술 부담: lightweight-charts, 실시간 시세 구독 계층, 거래정지·시세 지연 상태 표시.

### B · 돈 흐름 축

| 화면             | feature     | 티켓   |
| ---------------- | ----------- | ------ |
| 로그인 · 콜백    | `auth`      | 1-2    |
| 충전             | `account`   | 1-5    |
| 홈               | `home`      | 2-8    |
| 포트폴리오       | `portfolio` | 2-8    |
| 주문 · 매매 내역 | `order`     | 2-8    |
| AI 채팅          | `chat`      | 미발행 |

AI 슬롯 5종(브리핑, 원인 분석 ×2, 진단, 주문 전 점검, 채팅).
기술 부담: 멱등성 키 수명 관리, 주문 폼 Zod 검증, 커서 페이징, 진단 지표 SVG 그래프.

### 슬롯 개수가 안 맞는 것에 대해

B가 5종, A가 1종이다. **6종이 전부 일반 요청/응답이 된 뒤로 슬롯 하나의 구현량이 크게 줄었다.**
스트리밍 파서와 누적 상태 관리가 사라졌기 때문이다. 원인 분석은 홈·포트폴리오 양쪽에 들어가지만 컴포넌트는 하나다.
차트와 실시간 시세 구독 계층이 A에 통째로 들어가는 것이 무게를 맞춘다.

`account` feature가 두 축에 걸친다(충전은 B, 마이페이지·회차는 A). **파일이 겹치지 않게 하위 디렉토리를 먼저 나눈다.**

### 분담 전에 공동으로 끝낼 것

여기 합의 없이 갈라지면 **같은 컴포넌트가 두 개 생긴다.**

1. `auth` — 로그인 없이는 양쪽 다 화면을 못 본다. 한 명이 먼저 끝낸다
2. `shared/api` — HTTP 클라이언트, 401 갱신 인터셉터, 429 정책, 에러 정규화 어댑터
3. `shared/config` — 쿼리 키 팩토리, **AI 경로 상수**, 폴링 주기 상수
4. `shared/ui` 코어 — Button, BottomSheet, Skeleton, ErrorBoundary
5. 디자인 토큰 — 등락 의미 토큰 포함
6. 시세 구독 관리자
7. 종목 시세 행 컴포넌트

### 소유 경계

- `features/` 하위 폴더는 **한 사람 단독 소유**한다
- `shared/`는 **공동 소유**다. 여기를 건드리는 MR은 상대가 리뷰한다
- 상대 feature의 것이 필요하면 직접 import하지 않는다(ESLint가 막는다). `shared`로 올리자고 제안한다
